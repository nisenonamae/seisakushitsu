## ② 確かめた結果（この作業場の1台で）

### 一致（決め手①）

**a. 起動の設定を変えたとき（環境が違うときの当たり）** — 5通り（そのまま／`--disable-gpu`／SwiftShader 指定／GPU で描く指定／Canvas の GPU を切る）。

| 描く部品 | 5通りで同じ絵か |
|---|---|
| R1 Canvas 2D（ふつう・CPU 設定とも）| 9場面とも1画素も違わない。**ただし、この作業場には GPU が無く、R1 はどの設定でも CPU で描かれていたので、「GPU の端末でも同じ」とは言えない** |
| R2 CanvasKit CPU | 9場面とも1画素も違わない |
| R2 CanvasKit GPU | **WebGL の中身が変わると絵が変わった**（llvmpipe ↔ SwiftShader。どちらもソフトウェアの GPU）。違う画素 1.6〜23.6%、はっきり違う画素は最大 1.44%（⑥画像）、いちばん大きい差 250（⑥画像の nearest の縮小で、拾う画素が変わる）・129（②ふち）|

注：「SwiftShader 指定」「GPU で描く指定」は、ブラウザの報告では WebGL が llvmpipe のままだった（指定が効いていない）。実質は「llvmpipe」と「SwiftShader（`--disable-gpu`）」の2通りの比べ。

**b. 毎回同じになるか** — 設定5×場面9×描く部品4＝180通りを、同じページで2回＋ページを開き直して1回。**違ったのは 0通り**。

**c. 描く部品どうしの差**（そのままの設定。違う画素 % ／ はっきり違う〔差>8〕% ／ いちばん大きい差）

| 場面 | R1 ↔ R1(CPU設定) | R1 ↔ R2 CPU | R2 GPU ↔ R2 CPU |
|---|---|---|---|
| ① 字 | 同じ | 3.607 / 2.908 / 121 | 1.937 / 0.000 / 1 |
| ② ふち | 同じ | 3.367 / 0.000 / 8 | 4.205 / 1.725 / 138 |
| ③ ぼかし | 同じ | 36.527 / 0.041 / 61 | 67.286 / 0.020 / 15 |
| ④ 合成とマスク | 同じ | 29.639 / 0.101 / 99 | 38.145 / 0.073 / 55 |
| ⑤ グラデーション | 同じ | 0.720 / 0.000 / 1 | 48.463 / 0.005 / 36 |
| ⑥ 画像 | 同じ | 10.353 / 1.066 / 210 | 11.447 / 1.443 / 250 |
| ⑦ 線 | 同じ | 2.210 / 0.000 / 2 | 2.274 / 1.020 / 118 |
| ⑧ 小さな場面 | 同じ | 20.982 / 0.007 / 9 | 51.235 / 0.173 / 83 |
| ⑨ 重い場面 | 同じ | 25.764 / 0.085 / 91 | 59.464 / 1.916 / 92 |

読み方：
- **R1 と R2 CPU は別の絵**（当然）。ふち・線・グラデーションはほぼ同じ（差は 8 以下）。字は 2.9% がはっきり違う（字のふちの付け方・位置の細かさが違う）。画像は縮小・拡大の補い方が違う。→ 設計の方針どおり「下見と書き出しは同じ部品で」が要る。混ぜては使えない。
- **R2 の GPU と CPU も別の絵**。細い線・斜めの線・小さい形で、はっきり違う画素が 1〜2% 出る。→ 「GPU で下見・CPU で書き出し」は、画素の一致にはならない（見た目は近い）。

### 絵の質（決め手②）— `results/` の画像を自分の目で見た

- `results/01_scenes_a.jpg`・`01_scenes_b.jpg`：場面ごとに R1・R2 CPU・差を並べた物
- `results/02_zoom.png`：ふち・字・ぼかし・線・画像を5倍に拡大
- `results/03_gradient.png`：ゆるいグラデーションの色の帯（明るさの差を12倍に強調）
- `results/04_quality.jpg`：小さな場面（kurzgesagt 風に自分で組んだ物）を R1 と R2 CPU で

気づいたこと：
1. **ふち・線・角・重なりのなめらかさは、R1 と R2 CPU で見分けがつかない**（5倍に拡大しても同じ質）。小さな場面も、並べて差が分からない。
2. **色の帯**：R2 は、何もしないとゆるいグラデーションに**はっきり帯が出る**。`setDither(true)`（決まったざらつき）を付けると消え、R1 と 1 以内の差になった（R1〔Chrome〕は初めからざらつきを足している）。→ R2 では dither を必ず付ける（この試作ではふつうの設定にした）。ざらつきを足しても毎回同じ絵だった。
3. **透明のある画像の拡大**：R2 は、画像をそのまま渡すと、透明のふちが**黒ずんだ**。透明を先に掛けた形（premul）の画素にして渡すと直った（`harness.js`）。
4. **字が足りないとき**：字のファイルに無い字を描くと、**R1 は黙って端末の字で描き**（端末ごとに違う絵になる元）、R2 は描かない。設計の「読みこめていなければ描かずに不合格」には R2 のほうが合う。R1 で使うなら、描く前に「全部の字がファイルにあるか」を自分で確かめる必要がある。
5. **R2 GPU**：細い長方形（幅 0.5〜1）や斜めの細い線の濃さが CPU と少し違う。nearest の縮小は、WebGL の中身で拾う画素が変わる。
6. **ぼかし**：R1 と R2 で広がり方はほぼ同じ（差は最大 61、はっきり違う画素 0.04%）。変形で拡大した中のぼかしは、R2 は一緒に太る（割って戻した）・R1 は太らない。
7. 字：どちらも読みやすさは同じ。R2 は字を1つずつ置くだけ（詰め・合字なし）にして、R1 も詰めを切って合わせた。**詰め（カーニング）を入れた比べは未確認**。

### 速さ（決め手③）— この作業場（CPU 2コア・GPU なし）での数字。**端末では大きく変わるはず**

詰めて描く（書き出しの形）。1コマあたり ms・20コマの平均：

| 描く部品 | 重い場面：描く | 画素を取り出す | 合わせて | 小さな場面：合わせて |
|---|---|---|---|---|
| R1 | 991 | 6 | **997** | 908 |
| R1（CPU 設定）| 963 | 6 | **968** | 937 |
| R2 GPU（ここではソフトウェアの GPU）| 28 | 286 | **315** | 369 |
| R2 CPU | 513 | 6 | **519** | 834 |

- R1 は「描く」が実は溜めるだけのことがあり、取り出すときにまとめて描かれる（小さな場面では 描く 196＋取り出す 712）。**合わせた数字で比べる**。
- 画面に出しながら（ページの fps 測り・この作業場）：R1 0.9 fps／R2 GPU 3.3 fps／R2 CPU 2.0 fps。GPU の無い所の数字なので、**下見の速さの判断には使えない**。
- 効いた工夫：層（半透明・合成・ぼかしのまとまり）を画面いっぱいでなく**中身の囲みの大きさ**で作る。R2 CPU は重い場面が 13,200 → 約 500 ms になった（画面いっぱいの層1枚に約 125 ms かかっていた）。R1 はほとんど変わらなかった。この工夫で絵はわずかに変わる（R2 CPU：違う画素 0.015%・最大 5）。
- 重さの元：R1 は `ctx.filter` のぼかしが重い（ぼかしつき 22個で約 800 ms。R2 CPU は約 200 ms）。もっと速い書き方があるかは未確認。

コマを取り出す方法（P2 の下ごしらえ・1コマ 1920×1080）：
- 生の画素を取り出す：約 6 ms（R1・R2 CPU）。R2 GPU は約 290 ms（ここではソフトウェアの GPU なので遅い。本物の GPU では未確認）
- PNG にする（ブラウザの `toBlob`）：約 75 ms
- 生の画素（8.3MB）を base64 にして Python まで運ぶ：約 920 ms → **この運び方は遅い**。P2 では別の運び方（ブラウザの中でまとめてから渡す・通信の口を別に作る など）を試す必要がある

### CanvasKit の大きさと読みこみ
- `canvaskit.wasm` 7,317,345 バイト（gzip で 2,946,763）＋ `canvaskit.js` 120,877 バイト
- 読みこんで使えるまで：60〜100 ms（手元のサーバーから・裏のブラウザ。5回）。**GitHub Pages から・作り手の端末での時間は未確認**（ページが測って結果のファイルに入れる）

## ④ いまの時点でのおすすめと、その確からしさ

**おすすめ：R2（CanvasKit）を描く部品にし、「CPU で描く設定」を基準の絵（本番どおりに見る・書き出し）にする。** 軽い下見には同じ CanvasKit の GPU を使ってよいが、点検は必ず CPU の絵で行う。

確からしさ：**中くらい（作り手の端末の結果で、上がるか・ひっくり返る）**

理由（決め手の順）：
1. 一致：R2 CPU は、起動の設定を変えても・何度描いても、1画素も違わなかった。GPU を使う描き方（R2 GPU）は、WebGL の中身が変わるだけで絵が変わった。R1 は端末の GPU・ブラウザ任せで、こちらで固定できる所が少ない（字が足りないと端末の字で描く・Safari でぼかしが無い）。
2. 絵の質：R1 と R2 CPU は同じ水準。R2 は dither と premul の2つを必ず入れる（入れた）。
3. 速さ：この作業場では R2 CPU が R1 より速かった（層を小さく作る工夫を入れたあと）。ただし1台だけの数字。

ひっくり返る条件：
- R2 CPU が端末をまたいで一致しなかった → いちばんの強みが消える。R1 と同じ土俵になり、軽い R1 に傾く
- R1 が Mac・Chromebook でも書き出しとほぼ一致した（はっきり違う画素がほぼ 0）→ 追加の 7MB が要らない R1 でも足りる
- Chromebook で R2 CPU が遅すぎて「本番どおりに見る」が使い物にならない → 見方の作り（止めた1コマだけ CPU で描く、など）を考え直す

## ⑥ 本番に採る前に評価が要ること

1. 作り手の端末の結果で、③の1・2 を埋める（`使い方.md`）。R2 CPU が全部「同じ」かを最初に見る
2. 「見比べて分からない」の線を人の目で決め、数字にする（差の試しの合格の線）
3. 下見の作り：ふだんは GPU（軽い）・点検と止め絵は CPU、でよいか。GPU ↔ CPU の差（細い線で 1〜2%）を作り手が気にするか
4. 字：詰め・合字が要るなら CanvasKit の段落の機能を試す。または題の字を輪郭に変える
5. wasm に入っている部品の使用の条件を確かめる
6. 長い書き出しでのメモリと時間（P2 で）。コマの運び方（base64 は遅い）
7. Mac での書き出しが、この作業場と同じ絵になるか（R2 CPU なら同じ見込み。未確認）
8. この試作の決まりのうち、本番の「描く物の一覧」に持っていく物：ぼかしは最終の画素の単位／層は中身の囲みで作る／グラデーションは dither／画像は premul／字はファイルにある字だけ
