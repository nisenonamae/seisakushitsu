# 頼みごとの片づけ（Claude が毎時実行する手順）

制作室アプリの「頼みごと」（要約・題材探し・参考集め・構成・肉付け・図解など）を片づける。
アプリのデータは private のリポジトリ `nisenonamae/notion-daily` の `roadmap/apps/seisakushitsu/data.json` にある（同じリポジトリのほかのファイルはほかのアプリのものなので、絶対に触らない）。録画は `roadmap/apps/seisakushitsu/refs/` の下。

## 0. 用意
- `nisenonamae/notion-daily`（データ）と `nisenonamae/seisakushitsu`（アプリと道具）を用意する。セッションになければ add_repo ツールで push 権限つきで追加してクローン、あれば git pull
- `roadmap/apps/seisakushitsu/data.json` がまだないとき（アプリの同期がまだ）は、何もせずに「データがまだありません」とだけ報告して終わる

## 1. 仕事があるか見る
- `roadmap/apps/seisakushitsu/data.json` を読み、`jobs` の中で `status` が `"待ち"` で `deleted` でないものを、`createdAt` の古い順に最大 5 件取る
- **1件もなければ、すぐに「仕事なし」とだけ報告して終わる**（何も書き込まない）

## 1.5 進み具合を知らせる（必ず）
作り手はアプリで進み具合を見ている。仕事に取りかかるとき・区切りごとに、データを書き換えて **その都度 commit して push** する。
- 取りかかるとき：その job の `status` を `"作業中"`、`progress` を `{"done":0,"total":N,"label":"今やっていること"}` にして push
- 区切りごと：`progress.done` を増やし、`label` を次の作業に書き換えて push。途中で集まった結果（related・sources など）も、その時点で書き込んでおく（作り手は途中の結果から見始められる）
- `total` の目安：gather は「頼まれた項目の数＋1」（頼まれた項目を順に→仕上げ）、visual_ideas は 3（案を考える→見本を描く→仕上げ）、visual_make は 作る数＋1、video_make は 4、video_fix は 3、rebuild は 部分の数＋1、visual_fix と visual_redesign は 2、outline は 3、outline_fix・flesh・flesh_fix・flesh_sync・use_item は 2、footage_check は 3、title_ideas と title_fix は 2、thumb_ideas は 3、thumb_fix は 2、sound_ideas は 3、sound_fix は 2、digest は 2、script は 4、summary と script_fix は 2、pick は 4（集める→選ぶ→供給を測る→書く）
- 書き換えのたびに、その job の `updatedAt` も今の時刻（ミリ秒）にする

## 1.7 決まりごと（必ず読んで守る）
作り手が「こういうときは、こうして」と決めたことが、データの `rules[]` にある。`{"id","scope","when","do","active","from","createdAt","updatedAt"}`
- 仕事に取りかかる前に、`deleted` でなく `active` が true の決まりのうち、`scope` が「全部」か、その仕事に当たるものを全部読む（gather＝参考集め、pick＝題材探し、thumb_ideas・thumb_fix＝サムネ、sound_ideas・sound_fix＝音、title_ideas・title_fix＝題名、outline・outline_fix＝構成、flesh・flesh_fix＝肉付け、visual_ideas・visual_make・visual_fix＝図解、動画の組み立て＝動画。summary は「全部」だけ）
- 決まりはこの手順書の書き方より優先する。ただし「ほかのアプリのファイルを触らない」「著作権・利用規約」「事実の確かめ」の決まりは決まりごとより優先する（ぶつかるときは、守れなかったことを result に書く）
- 守った結果が分かるようにする（構成なら `change` や `memo` に「決まり『〜』に合わせた」など）
- **話し合い（talk）のとき**：作り手が「こういうときは」「毎回」「今後は」「いつも」のように、この制作だけでなくこれからも使う指示を言ったら、`rules` に `{"scope":（当てはまる仕事）,"when","do","from":"話し合い","active":true}` で足して push し、チャットで「決まりごとに入れました：〜」と一行で伝える。この制作だけの話か、これからもの話か迷ったら一言だけ聞く
- 決まりの文は作り手の言葉をなるべくそのまま使う。勝手に広げたり強めたりしない

## 2. 仕事の種類ごとのやり方
`candId` がない制作（`trial: true` のお試しなど）は、`projects[].title` を題材として使う。
JSON の中身はすべて ID でつながっている：`jobs[].projId` → `projects[].id`、`jobs[].matId` → `materials[].id`、`projects[].candId` → `candidates[].id`、`projects[].refs` → `ideas[].id`、`projects[].mats` → `materials[].id`、`projects[].recs[].path` → データのリポジトリの中の録画ファイル。

### summary（日本語のまとめ）
目的は、作り手が読んで分かることと、**このあと構成と肉付けを作るときの材料にすること**。
- `materials` の該当するものの `text`（動画の文字起こし）を読む。**元が英語・中国語など何語でも、まとめは必ず日本語で書く**（全文の翻訳はしない）
- 次の4つの見出しで `summary` に書く。【要点】だけは `size`（「3行で」「1分で読める量で」「見出しつきで詳しく」「数字と固有名詞を全部ぬき出して」）の量に合わせる
  - 【要点】この動画が言っていること
  - 【流れ】この動画の構成を、場面ごとに一行ずつ（つかみ→問い→…のように）。何秒あたりか分かれば添える
  - 【使えそうな事実・数字】数字・年・固有名詞は元の通りに残し、「（動画内の主張）」と分かるようにする。確かめが要るものは「要確認」
  - 【活かせそうな所】このチャンネル（地図・図解で「なぜ」を解く、素材なし）の構成や語りに使えそうな工夫を自分の言葉で
  - 【図解にできそうな場面】動画の中の実験・実演・模型・シミュレーションの場面ごとに「何秒あたり／何をしているか（装置・条件）／それで何が分かるか／図解でどう再現できるか」。実写や装置がなくても、図とアニメーションで同じことを見せる形にして書く。そういう場面がなければ「なし」
- 固有名詞は日本語の読み（カタカナなど）に、初めて出るときだけ原語を（）で添える
- 自分の言葉で言い換える。元の言い回しを長く写さない
- `status` を `"できた"` にする

### pick（題材探し）
- アプリのリポジトリの `tools/AUTO_PICK.md` の「数を指定されたとき」に従い、`n` 個の題材を `data/auto.json`（**アプリのリポジトリ**の方）に追加して push する

### gather（参考集め）
作り手が、集めたい項目に印を付けて頼む。題材（candidates の q・angle・links）について、頼まれた項目だけを集めて projects に書く。
**項目と数は `jobs[].counts`（style＝見せ方、content＝中身、sources＝資料、assets＝素材）に従う。数が 0 か、キーがない項目は集めない（手をつけない）。** counts そのものがないときだけ、下の4つ全部を下の数で集める。
1. **見せ方の参考** `related[]`（kind: "見せ方"）を 5〜8 本：同じか近い題材を、地図・アニメーション・シミュレーションで見せて伸びた動画。日本語・英語・中国語で YouTube を検索する（`tools/yt_common.py` の `search()` が使える。英語は `search(q,'en','US')`）。再生が多く、作りの質が高そうなもの（題名・チャンネル・サムネイルで判断。サムネイルは `https://i.ytimg.com/vi/<id>/hqdefault.jpg` で取れるので見てよい）
2. **中身の参考** `related[]`（kind: "中身"）を 3〜6 本：題材の中身を詳しく扱っている動画（言語は問わない）
3. **調べた資料** `sources[]` を 5〜10 件：公的機関・学術・百科事典など、事実を確かめられるウェブの資料。WebSearch と WebFetch で探す。`note` に、台本に使えそうな事実を自分の言葉で1〜2文（数字は出どころの通りに）
4. **使えそうな素材** `assets[]` を counts.assets 件（なければ 6 件）：題材の画面づくりに使える、自由に使ってよいとされている画像・地図・データ・映像。たとえば国や研究機関の公開データ、地理院タイル、Natural Earth、NASA などの公開画像、Wikimedia Commons の自由な使用が許された画像、著作権の切れた古い写真や絵。
   - 各要素：`{"title","url","source","license","terms_url","terms","credit","note"}`。`license` は書かれているライセンス名、`terms_url` は利用規約のページ、`terms` は規約の要点（出典の書き方、商用・加工・YouTube での利用がどう書かれているか）を一文で、`credit` は動画に載せる出典表記の例、`note` は動画のどこで使えそうか
   - 判断がつかないものは「要確認」と書く。最終の点検は作り手がする（作り手が `ok` を true / false にする）。`ok` は書かない
   - 実写や他人の作品で、自由な使用が明記されていないものは入れない
5. **参考動画の実写の出どころ**（counts.footage 本）：集めた参考動画（related。見せ方を先に、再生の多い順）のうち、実写の映像が使われていそうなものについて、下の footage_check と同じやり方で調べ、その related に `footage` を書く。すでに `footage` があるものは飛ばす
- related の各要素：`{"kind","title","url","channel","views","lang","why"}`（why は、なぜ参考になるかを一文）
- sources の各要素：`{"title","url","note"}`
- すでにある related・sources と同じ URL は足さない（もう一度頼まれたら、足りない分を追加する）
- 2回目以降の依頼は「もっと欲しい」という意味。すでにあるものとは違う切り口・言語・出どころから探す
- `result` には、頼まれた項目だけ「見せ方5本・素材5件を足しました」のように書く

### 編集スタイル（script のときに使う）
- `styles[]` は過去の動画の編集スタイル（型紙）。`{"id","name","origin","kata"}`
- script の job には `styleMode` と `styleId` が入っている
  - `"そのまま"`：`styleId` のスタイルの kata をそのまま型紙にする。録画や見せ方の参考は型紙には使わない（中身の資料は使う）
  - `"混ぜる"`：`styleId` のスタイルを土台に、今回の録画・見せ方の参考から良い所を足す。何を足したかを型紙の最後に「今回足したこと」として書く
  - `"新しく"`：過去のスタイルは使わず、今回の録画・見せ方の参考だけから型紙を作る（参考が足りなければ tools/STYLE_DEFAULT.md の決まりで補い、補った所を明記する）
- どの場合も、出来た型紙は `projects[].kata` に書く（作り手が最後に「残す」を選ぶと styles に入る）

### 構成と肉付けの形（outline・flesh 共通）
台本は「構成（骨組み）」→「肉付け」の2段階で作り、作り手が段ごとに印を付けて磨く。
- `projects[].outline` と `projects[].flesh` はどちらも `{"ver":数,"blocks":[段…],"memo":[決めたこと…],"history":[前の版…],"overall":"全体への注文","fixed":決まったか}`
- 構成の段：`{"id","role"（つかみ・問い・前提・仕組み・証拠・もしも・意外・まとめ・引き など短い名前）,"text"（何を言う・何が起きるか 1〜2文）,"show"（画面で何を見せるか 1文）,"aim"（見る人に起こしたいこと：驚く・納得する など一言）,"sec"（秒数の目安・数）,"change"（前の版から何をなぜ変えたか。初版は空）}`
- 肉付けの段：`{"id","oid"（もとの構成の段の id）,"osnap"（書いたときの構成の段の中身 `{"text","show"}` の写し。構成とのずれを見分けるのに使う。肉付けの段を書いたり書き直したりしたら、必ずその時点の構成の段の text と show で更新する）,"role","narr"（語り＝そのまま読み上げる文。話し言葉で、一文を短く）,"screen"（画面の指示：地図・図解・文字のどれで何を見せるか）,"check"（確かめが要る事実と出どころ。なければ空）,"change"}`
- **使った集めものを必ず書く**：各段に `"uses":[{"type","url","title","what"}]` を付ける。その段の中身や画面が、集めたもの（`sources`＝資料、`assets`＝素材、`related`＝参考動画、`materials`＝文字起こしの要約、`recs`＝録画、`ideas`＝参考メモ）のどれに拠っているかを、`type` に `source`・`asset`・`related`・`material`・`rec`・`idea` のどれか、`url` にその URL（なければ空）、`title` に題名、`what` に「何をそこから使ったか」（例：「時速8km・米粒でも同じ」「波が育つ早送りの見せ方」）を書く
  - materials（文字起こしのまとめ）を使ったときは `{"type":"material","id":materials の id,"url","title","what"}` と id も書く（アプリはこれで「使っている所」を出す）
  - 集めたものを使っていない段は `uses` を空にする（アプリに「なし」と出る）。使っていないのに書かない。事実を書いたのに出どころが集めたものにないときは、`check` に要確認と出どころを書く
  - 素材（assets）は作り手が「使う」にしたもの（`ok` が true）を優先。まだ点検されていないもの（`ok` がない）を使うときは `what` に「（未点検）」と添える。`ok` が false のものは使わない
  - 版を重ねても `uses` を正しく保つ（直した段は uses も見直す）
- 作り手が付ける印（読むだけ。意味を守る）：
  - `keep: true`（構成では「残す」、肉付けでは「いい」）→ その段の中身を**一字も変えない**。次の版でも `keep` を残す
  - `mark: "削る"` → その段を消し、前後のつながりを直す
  - `mark: "差し替え"` → 元の段は残したまま、`alts` に**違う方向の案を3つ**（段と同じ形の項目で）入れ、`change` に「代わりの案を3つ出しました」。作り手が選ぶ
  - `mark: "直す"` → `note` に従って直す（note がなければ、ほかの段とのつながりから良くする）
  - `mark: "追加"`（role も「追加」）→ `note` の頼みに従って新しい段として中身を書く。作り手が text / narr を書いていればそれを生かす
  - `edited: true` → 作り手が自分で書き換えた段。中身を変えない（明らかな誤字だけ直してよい）
  - `note`（段への注文）・`overall`（全体への注文）→ 従う。従わなかったときは `change` か `memo` に理由を一言
  - 並び順は作り手が並べ替えたもの。勝手に戻さない
- 新しい版を書くとき：①今の blocks を `history` の先頭に `{"ver","at","blocks"}` で入れる（15件まで）②`ver` を1増やす ③印のない段も、良くできるなら直してよいが、直したら必ず `change` に何をなぜ一言 ④書き終えたら、すべての段の `mark` と `note` を消す（`keep`・`edited` はそのまま。今回の差し替えで出した `alts` は作り手が選ぶまで残し、前からあった選ばれていない `alts` は消す） ⑤`overall` は反映したら空にし、反映した内容を `memo` に「〜にした」の形で足す
- `memo` は「話し合いや注文で決まった方針」の一覧（例：「つかみは実物の写真から入る」「数字は1段に1つまで」）。次の版でも守る。作り手は最後にこれを工夫の棚に残せる
- 長さは `jobs[].len`（または `projects[].len`）に合わせ、`sec` の合計を近づける。作り手があとから長さを変えたとき（`projects[].len` と今の合計が大きく違うとき）は、outline_fix で長さに合わせて段を足し引きし、`memo` に「〇分に合わせた」と書く。肉付けは1秒あたり約5.5字で合計の長さを見積もる

### outline（構成づくり・初版）
1. 題材（candidates の q と angle）、参考メモ（ideas）、資料（materials の summary と、必要なら元の text。【流れ】は構成の組み方の参考に、【使えそうな事実・数字】は中身に使う）、調べた資料（sources）、集めた参考（related）、使ってよいと点検された素材（assets の ok が true）を読む
2. 録画（recs）があれば ffmpeg でコマに分けて見る。なければ related の「見せ方」のサムネイルと `tools/STYLE_DEFAULT.md` をもとにする。上の「編集スタイル」の決まり（jobs の styleMode・styleId）に従って型紙を `projects[].kata` に書く
3. 構成の初版を `projects[].outline` に書く（ver 1）。段は 1分なら4〜6、10分なら10〜16、15分なら15〜22、20分以上なら20〜40 が目安。15分以上は、3〜6個の「章」に分けて、章ごとに小さな問いと答え（山場）を置き、途中で見る人が離れないようにする（`role` に「第2章：〜」のように章の名前を入れてよい）。中身が長さに足りないときは、水増しせずに足りない分を `memo` に書き、資料の追加（参考集め）か長さを縮めることを勧める。最初の15秒で問いと答えの気配を見せる。元の動画の構成をなぞらない
4. `memo` に、この構成で大事にした方針を2〜4個書く。`step` は 1 のまま
- progress の total は 3（材料を読む→型紙→構成）

### outline_fix（構成の直し）
- 上の「印」の決まりに従って次の版を書く。`result` に「3版：2段削り、1段に案を3つ」のように一言
- progress の total は 2

### flesh（肉付け・初版）
- 構成（`outline.blocks`。`fixed` でなくてもよい。作り手は構成・肉付け・素材を並行して進める。`mark` が「削る」の段は飛ばす）の段ごとに、肉付けの段を1つずつ書く（`oid` で対応させる。構成の text と show の意図を変えない）。語りは段の sec に収まる字数（sec×5.5字が目安）
- 事実と数字は sources・materials の通りに。確かめられないものは書かないか、`check` に「要確認：…（出どころ）」と書く
- `flesh` に ver 1 で書く。progress の total は 2

### flesh_fix（肉付けの直し）
- 構成の直しと同じ決まりで次の版を書く。total は 2

### flesh_sync（構成の変化を肉付けに反映）
構成があとで変わったとき、ずれた所だけを直す。ずれていない段には触らない。
- 構成の段ごとに、`oid` でつながる肉付けの段を見る
  - **肉付けまだ**（構成の段に対応する肉付けがない）→ 新しく書く（構成の順の位置に入れる）
  - **変わった**（肉付けの `osnap` と、今の構成の段の text・show が違う）→ 新しい構成に合わせて書き直し、`osnap` を更新、`change` に「構成の変化に合わせた：〜」。ただしその段が `keep`（いい）か `edited`（作り手が書き換えた）なら、中身は変えずに `alts` に書き直し案を1〜2個入れ、`change` に「構成が変わったので書き直し案を出しました」と書く（osnap はそのまま）
  - **消えた**（`oid` の構成の段がない、または「削る」の印）→ 肉付けの段を消す。`keep` か `edited` の段だったときは消さずに `change` に「構成から消えた段です。要らなければ削ってください」
- 肉付けの段の並び順は構成の順にそろえる
- 書く前に history に入れ、ver を1増やす（構成と肉付けの形の決まりと同じ）。total は 2

### use_item（集めものを使う：変更案を出す）
作り手が途中で見つけた・足した資料や素材を、今の構成か肉付けに入れたいときの頼み。**直接は書き換えず、段ごとの「変更案」を出す**（作り手が一つずつ採用・見送りを選ぶ）。
- job：`item`（`{"type","url","title"}`。projects の sources・assets・related のどれか）、`target`（"o"＝構成／"f"＝肉付け）、`blocks`（作り手が選んだ段の id。空なら自分で使える所を探す）、`note`（どう使いたいか）
- まず item の中身を読む（URL を開く。素材なら何が写っているか・利用条件）。使い道がなければ、案を出さずに result に「使える所が見つかりませんでした：理由」と書く
- `projects[].proposals[]` に案を足す：`{"id","batch"（この job の id）,"kind"（"o" か "f"）,"op"（"change"＝書き換え／"insert"＝新しい段を足す／"delete"＝消す）,"bid"（対象の段の id。insert ならこの段の下に入る。先頭なら null）,"after"（change と insert のときの新しい段の中身。段と同じ形で、必ず `uses` にこの item を入れる。肉付けの段なら oid と osnap も）,"why"（なぜこう変えるか一文）,"from"（item の `{"type","url","title"}`）,"status":"提案","updatedAt"}`
- 案は少なく・小さく。item を入れるのに必要な段だけ。ほかの段は案に入れない（＝そのまま残る）
- `blocks` が指定されていればその段への案を中心に。`keep` や `edited` の段は、`blocks` で指定されたときだけ案を出す
- 構成への案を出したら、肉付けはアプリが自動で「ずれ」として見せるので、肉付けの案まで出さなくてよい
- total は 2。result に「変更案を3つ出しました（構成 2・5段、新しい段1つ）」のように

### footage_check（実写の出どころ調べ：フリー素材か）
参考動画（`jobs[].relUrl`＝projects の related の url）か、作り手の録画（`jobs[].recPath`＝projects の recs の path）に出てくる**実写の映像**が、ネット上の自由に使える素材（フリー素材）かを調べる。
- 見る材料：録画があればそれを ffmpeg でコマに分けて見る（1秒に1枚＋場面の変わり目。いちばん確か）。参考動画なら、その動画の録画が recs にあればそれを使い、なければ **YouTube が自動で作る途中のコマ** `https://i.ytimg.com/vi/<id>/maxres1.jpg`・`maxres2.jpg`・`maxres3.jpg`（動画のおよそ1/4・1/2・3/4の所。1280×720。取れなければ `sd1`〜`sd3`、`hq1`〜`hq3`）とサムネイル（`hqdefault.jpg`・`maxresdefault.jpg`）を curl で取って見る。これで録画がなくても4枚ほどは自動で見られる（ただし動画の一部だけなので、`note` に「途中の3コマとサムネで調べた。ほかの場面は録画があれば調べられる」と書く）。あわせて YouTube 検索の結果に出る説明文の一部（`tools/yt_common.py` の search で題名を検索）を見る。YouTube の動画ページそのものはこの環境から開けないので、開こうとしない
- 実写の場面ごとに、何が写っているか（例：「砂利道を走る白い四駆を後ろから」「研究室の回転する円形の道」）を短く言葉にする。アニメーションや図だけなら `verdict` を「実写なし」にする
- その言葉で、自由に使える素材のある所を探す：Wikimedia Commons（API が使える）、NASA の画像・映像（images-api.nasa.gov）、Internet Archive のパブリックドメイン、各国の政府や研究機関の公開映像、Pexels・Pixabay・Mixkit・Videvo などの無料素材サイト（WebSearch で「site:pexels.com gravel road car」のように探す。サイトによってはこの環境から開けないので、検索結果の題名・説明・サムネイルで判断する）。説明文やクレジットに出どころ（Pond5・Storyblocks などの有料素材、研究者の名前など）が書かれていれば、それを手がかりにする
- 見つけた候補は、見られるならサムネイルや見本の画像を取ってきて、元の場面と見比べる。判定（`match`）は正直に：「同じ映像」（構図・動き・写っている物がはっきり一致）／「似た映像」（同じ題材だが別の撮影）。確かめられないのに「同じ」と言わない
- その related（または recs の要素）に `footage` を書く：`{"checkedAt","note"（全体の一言。例：「冒頭の3場面が実写。2つは似たフリー素材あり、1つは有料素材の可能性」）,"shots":[{"desc","at"（録画なら秒数、分かれば）,"verdict"（「フリー素材で見つかった」「似たフリー素材あり」「見つからない」「実写なし」）,"found":[{"site","title","url","license","terms"（商用・加工・YouTube での利用・表記の要点を一文）,"match","free"}]}]}`
- **`free: true` は「フリー素材と確定」の印**。アプリでは緑の「✓ フリー素材と確定」と目立たせて出す。付けてよいのは、`match` が「同じ映像」で、**かつ**その素材のページ（または規約）で、収益化した YouTube 動画に使ってよい無料のライセンスだと確かめられたときだけ。サイトに複数のライセンスがあって、その素材がどれか確かめられないとき（Mixkit の無料／制限付きなど）や、似た映像のときは付けない（`free` を書かないか false）
- 見つかったフリー素材は `assets` にも足す（gather の素材と同じ形。`note` に「参考動画『〜』の〇〇の場面と同じ（似た）映像」。`ok` は書かない）。ライセンスがはっきりしないものは「要確認」
- total は 3（場面を見る→探す→書く）

### title_ideas（題名の案）
- 読むもの：題材と切り口、構成・肉付け（あれば）、`related` の参考動画の題名と再生数（伸びた題名の型を学ぶ。そのまま訳さない）、決まりごとの「題名」、餌箱の学び
- `n` 個の案を `projects[].titles[]` に `{"id","text"（題名）,"hook"（引きの型：問い／意外な事実／数字／もしも／ひっくり返し など一言）,"why"（なぜ押したくなるか一文）,"uses","updatedAt"}` で足す。型が偏らないようにばらす
- 日本の YouTube で読まれやすい長さ（30字前後まで。大事な言葉は前半）にする。中身と合わない釣り題名・事実の盛りすぎはしない
- `jobs[].wish` があれば従う

### title_fix（題名の別案）
- `jobs[].titleId` の題名を元に、`jobs[].notes`（なければ「同じねらいで言い回しを変える」）の方向で、別案を3〜5個 `titles[]` に足す（各案に `"parent": 元の id`）

### thumb_ideas（サムネの案）
- 題名が決まっていれば（`projects[].titleId` の titles の text）、**その題名と並べて見たときに押したくなるサムネ**にする。題名と同じ文字をサムネに繰り返さない（題名の続きや、題名にない一言・数字・絵で引く）。`title` には組み合わせる題名を入れる

- 読むもの：題材、構成・肉付け（あれば）、`related` の参考動画のサムネイル（`https://i.ytimg.com/vi/<id>/hqdefault.jpg`。伸びたものほどよく見る）、決まりごとの「サムネ」（`ex` の見本も開く）、餌箱の学びのうち area が「サムネ」のもの
- `n` 個の案を出す。案ごとに、**題名とサムネを組で**考える：`projects[].thumbs[]` に `{"id","idea"（ねらいを一言）,"title"（動画の題名案）,"text"（サムネに載せる文字。短く）,"desc"（どんな絵か一文）,"preview"（1280×720 の PNG。`roadmap/apps/seisakushitsu/thumbs/<projId>/<id>.png`）,"src"（描いたプログラムのパス）,"uses"（構成の段と同じ形）,"status":"提案","updatedAt"}`
- 絵はプログラムで描くか、assets のうち `ok` が true のものだけを使う。実在の人物の写真・他人の作品・ロゴは使わない
- 参考動画のサムネをそのまま真似ない（構図や色の考え方を学ぶだけ）。題名で事実を盛らない（動画の中身と合っていること）
- `jobs[].wish` があれば従う。total は 3

### 音の保管庫（データの `sounds[]`）
BGM・効果音・始まりの音・環境音をためておく所。音のファイルはデータのリポジトリの `roadmap/apps/seisakushitsu/sounds/<種類>/` に置く。
- 形：`{"id","kind"（BGM／効果音／始まりの音／環境音）,"name","mood"（雰囲気・使いどころ）,"tags":[],"source"（出どころ）,"license"（使い方の条件）,"credit"（概要欄に書く表記。要らなければ空）,"file"（パス）,"len"（秒）,"usedIn":[{"projId","where"}],"by"（作り手／Claude）,"createdAt","updatedAt"}`
- 音を付けるときは**まず保管庫から選ぶ**。同じチャンネルで同じ音が続くのは個性になるので、むしろ使い回してよい（とくに始まりの音・決まった効果音）
- 足りない音は、自由に使えるもの（パブリックドメイン・CC0・クレジット表記で使えるもの・商用可の無料素材）を探すか、プログラムで作る。使う前に利用規約を読んで `license`・`credit` に書く。YouTube の収益化で問題になる条件（収益化不可・要申請など）のものは使わない
- 使った音は、その動画を `usedIn` に足す。新しく入れた音は保管庫に残す（消さない）

### sound_ideas（音を付ける）
- 読むもの：決まりごとの「音」、保管庫、肉付けの段ごとの語りと役割（序・章・見せ場・結び）、仮の動画、job の `wish`
- 段（章）ごとに BGM を決め、見せ場や切り替わりの効果音、冒頭の始まりの音を決める。語りの声より目立たせない（BGM は声の下で −20dB 前後、声のない間だけ少し上げる）
- `projects[].sound`＝`{"cues":[{"soundId","where"（「序の頭」「第2章の全体」「2-3 の車が止まる所」など）,"block","at"（秒・任意）,"vol"（dB）}],"note"（ねらいを一言）,"video"（音を入れた動画のパス）}` を書き、音を入れた動画を書き出して `video` に置く。total は 3
### sound_fix（音の直し）
- `jobs[].notes` に従って `projects[].sound` を直し、動画を書き出し直す。直しのうち「次の動画でも同じように」と読めるものは、決まりごと（scope：音）に足す。total は 2

### thumb_fix（サムネの直し）
- `jobs[].thumbId` のサムネを `jobs[].notes` に従って直す。題名・文字・絵・色・配置のどれでも。新しい画像は `<id>_p<番号>.png`、`preview` を更新し、古いパスは `previews` に残す
- `thumbs[].fixlog` の該当（`jobs[].fixId`）に `after`・`status: "できた"`・`reply`（どう直したか一文）を書く。total は 2

### digest（餌の消化：作り方を育てる）
制作とは別に、作り手が「うまい」と思った動画・文章を餌として入れたもの。データの `feeds[]`：`{"id","kind"（動画の文字起こし／文章／録画／メモ）,"title","url","text","rec"（録画のパス）,"focus"（学ばせたいこと：構成・肉付け・見せ方・サムネ）,"why"（作り手がいいと思った所）,"status","lessons":[]}`
- `jobs[].feedId` の餌を読む（録画なら ffmpeg でコマに分けて見る）。`why` があれば、そこを中心に
- `focus` の分野ごとに、このチャンネル（地図・図解で「なぜ」を解く、素材なし）で**使える学び**を取り出し、`lessons` に `{"area"（構成／肉付け／見せ方／サムネ）,"text"（どうすればいいか。次の動画でそのまま使える形で一文〜二文）,"why"（餌のどこでそう分かったか。自分の言葉で短く。元の文を長く写さない）,"example"（このチャンネルならどう使うか一文）}` で書く。分野ごとに2〜5個。当たり前のこと（「分かりやすく話す」など）は書かない
- `status` を「消化済み」に。total は 2
- 構成・肉付け・図解・サムネを作るときは、決まりごとに加えて、`feeds` の `lessons` のうち `drop` が true でないものを引き出しとして見てよい。使ったら、その段の `uses` に `{"type":"feed","title":餌の題名,"what":学び}` と書く

### video_make（仮の動画づくり）
声・図解・字幕まで入った下書きの動画を作る。作り手はこれを見て直す所を書く。
1. `bash tools/setup_voice.sh`（声の用意。初回は数分。GitHub の API は使えないのでリリースの直リンクで落とす）
2. **全部の段の画面を作る（絵コンテのカードを出さない）**：肉付けの各段に `shots`（文ごとのカード割り。`tools/vis/README.md` の「カット」の決まりに従う。一つの画面は 3〜6 秒、止まった画面を作らない）を書く。カットの始まりは `at`（語りの言葉）で決め、語りの順番どおりに画面を出す（語りより先に出さない）。文字だけの画面は作らない。写真は 1 分あたり 4 枚以上集めて挟み、`punch`（ぐいっと寄る）は寄って見たほうが分かる所だけに使う。記録映像（アーカイブ・Mixkit の無料ライセンス）も探して入れる。使った写真のライセンスと作者は `p.video.credits` に並べる。`shots` を書かない段だけ、代わりに `scene`（図解の部品の指定。`tools/vis/README.md` の表から選ぶ）を書く。段の「画面の指示」をいちばんよく見せられる部品と指定を選ぶ。合う部品がなければ `tools/vis/scenes.py` に部品か `mode` を足す（足したら README の表にも書く）。書いたら `python3 tools/make_scenes.py --data <data.json> --proj <projId> --repo <notion-daily の場所>` で全段の画面を作る（作った段には構成の段の `visual` が付く。すでに `visual` がある段は飛ばす。作り直すときは `--force`）。作った画面のうち何枚かをコマで見て、おかしければ直してから次へ
3. `python3 tools/render_draft.py --data <data.json> --proj <projId> --repo <notion-daily の場所> --out <notion-daily>/roadmap/apps/seisakushitsu/videos/<projId>/draft_v<版>.mp4 --voice <声> --speed <速さ>`
   - 声は `projects[].voice`（なければ 2＝四国めたん ノーマル）、速さは `projects[].speed`（なければ 1.1）
   - 肉付けがあればその語り、なければ構成の text を読む。段に `visual`（作った図解の .mp4 か見本の .png のパス）があればそれを映し、なければ「画面の指示」を書いた絵コンテのカードを出す
4. できた mp4 が 95MB を超えたら、`-crf` を上げて作り直す（GitHub の1ファイルの上限が100MB）
5. `projects[].video` に `{"path","ver","duration","blocks"（出力と同じ名前の .json の blocks。段ごとの開始・終了秒）,"voice","at","reply"}` を書き、前の `video` は `projects[].videoHistory` に足す。mp4 と json を commit して push。`projects[].builtAt` を今の時刻、`builtLen` を `projects[].len` にする（「前に作ったあとで変わったこと」の起点になる）
- 作った画面の mp4 と、`scene` を書いた data.json も commit して push する
- 動画を置いたら、`render_draft.py` が出す `<出力>.json` の `blocks` と `shots`（場面の番号・始まり・終わり）を `p.video.blocks`・`p.video.shots` に入れる
- total は 4（声の用意→画面→組み立て→置く）

### video_fix（動画の直し）
- `jobs[].fixes` は `[{"sec":"2:10","text":"ここをゆっくり"}]`。`sec` は時間（「2:10」）か場面の番号（「3-4」）。時間なら `projects[].video.blocks` から何段目かを、場面の番号なら `projects[].video.shots` の `tag` からそのカットを見つける
- 直しの中身で、直す所を選ぶ：語りの言い回し・速さ・間 → 肉付けの段（`narr`）／話の順番・ある段が要らない・足りない → 構成（直したら flesh_sync と同じやり方で肉付けも合わせる）／絵・図解 → その段の図解（visual_fix と同じやり方）／声の速さ全体 → `projects[].speed`
- 作り手がはっきり頼んだ直しなので、`keep` や `edited` の段でもその点は直してよい（直した段の `change` に「動画の直し：〜」）。直す前の版は history に残す
- 直したら video_make と同じやり方で作り直し（ver を1増やす）、`projects[].fixes` の該当する行に `done: true` と `reply`（どう直したか一文）を書く。`video.reply` に全体の一言
- **直しを次の動画にも残す（いちばん大事）**：直しを一つずつ「この動画だけの話」か「これからも毎回の話」かに分ける。`always: true` の直しは必ず「毎回」。印がなくても、見せ方・動き・文字・声・間・写真の使い方など、別の題材でも同じことが起きそうな直しは「毎回」と判断してよい（「2:10 の数字が違う」のような、その動画の中身だけの話は「この動画だけ」）
  - 「毎回」の直しは二つの所に残す。①`rules` に `{"scope":"動画"（図解の見た目なら "図解"）,"do":作り手の言葉ほぼそのまま,"from":"動画の直しから","ex":{"before":直す前,"after":どう直したか}}` を足す ②部品やカット割りの作り方（`tools/vis/*.py`・`tools/vis/README.md`・この手順書の video_make）そのものを直して、次からは何も言われなくてもそうなるようにする。②ができたら決まりの `ex.after` に「部品の◯◯を直した」と書く
  - `projects[].fixes` の該当行に `ruled: true` を書き、`reply` の最後に「（これからも毎回そうします）」と付ける
  - 動画づくり（video_make・video_fix・rebuild）の前には、scope が「動画」「図解」「全部」の決まりを全部読み、カット割りと部品の指定がそれに合っているか確かめてから作る
- total は 3（直す→作り直す→置く）

### 人に見せる前の点検（video_make・video_fix・rebuild のどれでも必ず）
作り手の手間を減らすための一番大事な手順。直しを言われた所だけでなく、**動画の全部の場面**を毎回点検する。
1. `python3 tools/lint_shots.py <data.json> <プロジェクトid> <書き出した .json>` を走らせ、出た指摘を全部直すか、直さない理由を `reply` に書く
2. 書き出した動画から、各場面の始めと終わり近くのコマを並べた一覧を作り、**自分の目で**決まりごと（scope：動画・図解・全部）を一つずつ照らし合わせる。特に：文字が残っていないか／字幕と画面の順番・同じ文言／使い回し／一瞬の画像／はみ出し・途切れ・不自然な位置／音が動きと合っているか
3. 説や仕組みを絵にする場面は、元の資料（文字起こし・記事）を読み直し、何を言っている説なのかを自分の言葉で一文にしてから描く（分からないまま描かない）
4. 点検で見つけて直した数を `reply` に書く（作り手がどれだけ点検の手間を減らせているかの目安）
5. 機械で見つけられる種類の直しを新しく受けたら、`lint_shots.py` にも足す
6. 書き出しの記録に「［点検］…画面の中でいきなり現れる／消えるもの」が出たら直す（ブラウザの場面は、車・車輪・重機の四角を一コマずつ記録し、画面のふちに触れずに出入りしたものを自動で見つける。新しい乗り物の絵を作ったら、描く関数の中で `track(x0,y0,x1,y1)` を呼ぶ）

### rebuild（情報を変えて作り直す）
作り手が一度作ったあとに、資料・素材・決まりごと・餌箱・長さなどを変えて、その情報を入れて作り直したいときの頼み。
- job：`all`（true なら全部作り直す）、`parts`（作り直す部分：outline・flesh・visual・title・thumb・video）、`keepMarks`（true なら `keep`（残す・いい）の段と `edited`（自分で書き換えた）段はそのまま守る）、`notes`（どう良くしたいか）、`changes`（前に作ったあとで変わったことのうち、作り手が入れたいと選んだもの）、`len`
- まず `changes` と `notes` を読み、それぞれをどの部分のどこに入れるかを決める（例：新しい資料 → 構成の第2章に段を足す、肉付けの数字を差し替える／新しい決まりごと → 全体に当てはめる／長さ → 段の足し引き）
- `parts` を outline → flesh → visual → title → thumb → video の順に作り直す。どの部分も、作り直す前の版を history に入れてから書く（ver を1増やす）。各段の `change` に「作り直し：〜を入れた」と、何の情報で変わったかを書く
- `keepMarks` が true なら守る段は中身を変えない（入れたい情報がその段に関わるときは `alts` に案として出す）
- `all` でないときは、頼まれていない部分には触らない。前の部分を変えたことで後の部分とずれても、アプリがずれとして見せるので、そのままでよい（ただし `video` が頼まれていれば、最後に今の状態で作り直す）
- visual：今の構成で図解が要る段を見直し、新しい情報で必要になった図解の案を足し、見せ場は作る（visual_ideas・visual_make と同じ）
- title・thumb：案を足し、いちばん良いと思うものを仮に `titleId`・`thumbId` にする（前の選択は result に書いて残す）
- 進み具合：total は「部分の数＋1」。部分が一つ終わるごとに push する。重くて1回で終わらないときは、終わった所まで push して `status` を「待ち」に戻し、`progress.label` に「〇〇まで作りました。続きは次の回」と書く
- 終わったら `projects[].builtAt` を今の時刻、`builtLen` を今の長さにする。`result` に、何の情報をどこに入れたかを短く

### 話し合い（talk）——チャットで作り手と直接話して磨く
作り手が「Claude と話し合う」を押し、チャットに依頼文を貼ったときの手順。対象（制作の id と、outline か flesh か）は依頼文に書いてある。
1. 用意（0. と同じ）のあと、対象の制作の構成または肉付けと、付いている印・注文・memo、題材と資料を読む
2. 印や注文が付いていれば、まず上の決まりで次の版を書いて push する（アプリは自動で読み直す）。付いていなければ書かずに 3 へ
3. チャットで作り手に返す。短く：①変えた所（あれば）②今の構成・肉付けの**弱いと思う所を自分から**2〜3個、具体的な代わりの案つきで（「4段目の説明が長い。図で一発で見せる案A／省いて結論を先に出す案B」のように）③迷っている所を選びやすい問いで1〜2個
4. 以後、作り手の返事のたびに：決まったことを反映した次の版を書いて push し、決まった方針は `memo` に足す。チャットの返事は短くし、「〇版にしました。次は〜をどうしますか」と次の一手を出す。作り手が迷っていたら、自分の意見をはっきり言う（言われた通りに直すだけにしない）
5. 作り手が「決まり」と言ったら、アプリの「決まり」ボタンを押すよう伝える（自分では fixed にしない）
- 書き込みの決まり（3.）を守る。進み具合（1.5）は不要。job は作らない
- 作り手がアプリで同時に印を付けていることがあるので、書く直前に必ず pull し、その間に付いた印・注文も読んで反映する

### visual_ideas（図解の案）
- 台本（projects の script）と型紙（kata）、作り手の希望（jobs の wish）を読み、台本の中で「動く図・地図の動き」で見せると分かりやすくなる場面について、`n` 個の案を考える
- 案ごとに、見本の静止画（1280×720 の PNG。いちばん見せ場になる瞬間を1枚）をプログラムで描き、データのリポジトリの `roadmap/apps/seisakushitsu/visuals/<projId>/<案のid>.png` に置く
- `projects[].visuals[]` に `{"id","idea"（一言の名前）,"desc"（何をどう動かすか、台本のどこで使うか、二文まで）,"preview"（PNG のパス）,"uses"（構成の段と同じ形。どの集めものから何を使ったか）,"note"（台本がまだないときは「台本がまだないので、題材と集めた資料から考えた案」）,"status":"提案","chosen":false,"updatedAt"}` を足す
- 台本（script）も構成も肉付けもまだないときは、題材と sources・related から案を考える
- **参考動画の実験・実演を図解で再現する案を必ず検討する**：materials の summary の【図解にできそうな場面】、related の動画の途中のコマ（`https://i.ytimg.com/vi/<id>/maxres1.jpg`〜`maxres3.jpg`）、作り手の録画（recs）を見て、実験や実演があれば、それを図とアニメーションで見せる案を入れる（実験の装置そのものを描き写すのではなく、何が起きて何が分かるかを見せる）。`uses` に、どの動画の何秒あたりの実験か（`{"type":"material","id",...,"what":"8:01 速くすると波が出る実験"}`）を書く
- `jobs[].fromMat` があるときは、その資料の【図解にできそうな場面】から案を作る（`n` 個まで）
- 型紙の色づかい・文字の決まりに合わせる。使う素材は assets のうち `ok` が true のものだけ

### visual_make（図解を作る）
- `jobs[].ids` の案を、それぞれ短い動画（1280×720、30fps、5〜15秒、H.264、1本 15MB 以内）として作る。作り方：Python（numpy・Pillow など）でコマを描き、ffmpeg でつなぐ。地図は Natural Earth・地理院タイルなど ok の素材だけを使い、画面の隅に出典を入れる
- `roadmap/apps/seisakushitsu/visuals/<projId>/<案のid>_v<版>.mp4` に置き、その visual の `clip` にパス、`ver` に版、`status` を `"できた"` にする。1本できるたびに push する（作り手は届いた順に見られる）
- 台本の中で使う段が分かれば、visual の `oid` に構成の段の id を書き、その構成の段に `visual`（clip のパス）を付ける（仮の動画でその段にこの図解が映る）

### visual_fix（図解の直し）
- `jobs[].visualId` の図解を `jobs[].notes` に従って直し、版を1つ上げた新しいファイルとして置き、`clip`・`ver` を更新し、`status` を `"できた"` にする
- `visuals[].fixlog` の中で `id` が `jobs[].fixId` のものに、`after`（新しいファイルのパス）と `status: "できた"` を書く。直しきれなかった所があれば `reply` に一言

### visual_redesign（見本の直し：アイデアはそのまま、デザイン・見せ方だけ）
- `jobs[].visualId` の案（status は「提案」のまま）の見本を、`jobs[].notes` に従って描き直す。**何を見せるか（アイデア）は変えず**、色・大きさ・向き・配置・文字・見せ方だけを直す
- 新しい見本は `visuals/<projId>/<id>_p<番号>.png`（番号は 2 から順に）に置き、`preview` を新しいパスに、古いパスは `previews`（配列）に残す。`desc` の見せ方の部分も直しに合わせて書き換えてよい
- `fixlog` の該当（`jobs[].fixId`）に `after` と `status: "できた"`、`reply`（どう直したかを一文）を書く。total は 2

### 図解の共通の決まり
- 見本や図解を描いたプログラムは、同じ場所に `<id>.py`（何本かまとめたなら `previews.py` など）として置き、`visuals[].src` にそのパスを書く。直すときは、それを読んで直す（一から描き直さない）
- 「図解」の決まりごと（rules の scope が「図解」）を必ず読む。`ex`（前後の見本と例の名前）が付いた決まりは、その見本も開いて、どう直したかを見てから守る


### script（台本づくり・古い形。今は outline → flesh を使う）
1. 題材（candidates の q と angle）、参考メモ（ideas の memo・時間・効く場所）、資料（materials の summary、なければ text）、調べた資料（projects の sources）、集めた参考（projects の related）を読む
2. 録画（recs の path）があれば ffmpeg でコマに分けて見る。録画がないときは、related の「見せ方」のサムネイルと、アプリのリポジトリの `tools/STYLE_DEFAULT.md`（標準の型紙）をもとにする（例：1秒に1枚、場面の変わり目も拾う）。画面の切り替わる間隔、地図の寄り方と動きの速さ、字幕の位置と大きさ、色、語りのテンポを読み取る
3. 上の「編集スタイル」の決まりに従って、型紙を `projects[].kata` に箇条書きで書く
4. 10分ほどの台本を `projects[].script` に書く。形：
   - 冒頭の問い（最初の15秒で問いと、答えの気配を見せる）→ ふつうの答え → 本当の答え → 意外な広がり → 結び
   - 段落ごとに【画面】（地図やアニメーションで何を見せるか）と【語り】を書く
   - 事実と数字には出どころ（資料の題名、または公的な資料の名前）を添える。確かめられないものは「要確認」と書く
   - 元の動画の構成や言い回しをなぞらない
5. `scriptVer` を 1 にし、`step` を 2（台本を確かめる）にする

### script_fix（台本の直し）
- `jobs[].notes`（作り手の直し）に従って `projects[].script` を直す。`scriptVer` を 1 増やす。直さなかった点があれば `jobs[].result` に一言書く

## 3. 書き込みの決まり
- 片づけた仕事は `status` を `"できた"`、`result` に一言（例：「台本 1版を届けました」）。できなかったら `status` を `"失敗"`、`error` に理由
- 書き換えた要素（jobs・materials・projects など）は、**必ず `updatedAt` を今の時刻（ミリ秒の数字。例：Python の `int(time.time()*1000)`）にする**（アプリはこれで新しい方を選んで合わせる）
- 書き換えるのは該当する要素だけ。ほかの要素や並びはそのまま残す。JSON は Python で読み書きし、`ensure_ascii=False` で保存する
- commit して push する。push が断られたら、pull し直して最新のファイルに同じ書き換えをもう一度当ててから push する（ファイルを丸ごと上書きしない）
- コミットの作者は `Claude <noreply@anthropic.com>`

## 声の調整室（voice.html ／ データは `roadmap/apps/seisakushitsu/voice.json`）
作り手が Mac で声を調整して残したものを読み、声の作り方を育てる。作り手に「声の調整を見て」と言われたとき、または頼みごとの片づけのついでに行う。
- `voice.json` の中身：`kata[]`（声の型。`main: true` がチャンネルの声）、`takes[]`（保存した調整）、`lines[]`（練習の文）、`vrules[]`（読み方の決まり＝Claude の案の作り方）
- `takes[]` の `status` が「Claude まだ」のものを古い順に読む。各 take には文ごとに `base`（エンジンのまま）・`claude`（決まりを当てはめた案。自分で調整のときは null）・`q`（作り手が仕上げたもの）、`scene`（場面）、`memo`、`kata`（そのときの型）が入っている
- 読み方：`q` と `claude`（なければ `base`）を一音ずつ比べ、どこを・どれだけ・どの向きに直したかを数字で出す（高さは半音＝ln2/12、長さは比、間は秒）。メモと場面を合わせて、**同じ場面で何本か同じ向きの直しが続いたら** `vrules` に決まりとして足すか、数を直す（1本だけで決めない。1本だけのときは take の `reply` に「〜と読みました。もう1〜2本同じ直しがあれば決まりにします」と書く）
- 決まりの種類（voice.html の applyRules と tools/voice_render.py の apply_rules に同じものがある。新しい種類を足すときは両方に足す）：`global`（速さ・抑揚・音量・前後の間）、`end_fall`（文末を下げる：n 音・amt）、`question`（？の文末を上げる：amt）、`comma_pause`（読点の間を足す：add）、`emph`（《》の所を上げて伸ばす：up・stretch）、`first_up`（最初の句を上げる：amt）。`scene` を入れるとその場面だけに効く
- 仕上げ：読んだ take は `status` を「読んだ」、`reply` に一言（何を学んだか・決まりをどう変えたか）。決まりを足したら `vrules[].from` に元にした take の id、`memo` に作り手のメモの言葉。文章で残すべき学び（「問いかけのときは〜」）は data.json の `rules` に scope「音」で足す
- 型（kata）の直しは作り手が決めるもの。Claude は型を勝手に変えない
- 本番の動画の声：`python3 tools/render_draft.py ... --kata main --vrules`（先に `bash tools/setup_engine.sh`）。調整室で聞いた音と同じ手順で作る（tools/voice_render.py）
- 「Claude の案から」の take の `fromClaude`（直した量）が 0.1 を切るのが続いたら、作り手に「声は Claude だけで作れそう」と伝える
- 動画の語りの文を調整室で調整して保存したもの（take の `src` に projId・blockId）は、`render_draft.py --kata` のとき、同じ文（《》を除いた文字が同じ、元の声も同じ）ならその読み方（`q`）をそのまま使う。語りの文を書き換えたら、その文の調整は使われなくなる（作り手に一言伝える）
- 調整した文で書き出したとき、`［点検］調整した文の長さが変わった` が出た段は、カットの切り替わり（at）・字幕・ats は語りに合わせて自動で動くが、**決まった長さで動くアニメ**（車が横切る・数字が増える等）が急ぎすぎ・間延びしていないかを見本の画像（revsheet）で見て、ずれていれば shots の hold・beat・at を直す。作り手が付けた間（pause）の所で画面が止まって見えるなら、その間に小さな動きを入れる
- `voice.json` の `notes[]`（調整のメモ）：声づくりのコツ。Claude が記事などから集めたもの（`by:"Claude"`、`claude` に見立て、`src` に出どころ）と、作り手が書いたもの（`by:"作り手"`）。声を作る・決まりを直すときに読む。作り手から声の参考（記事・動画）をもらったら、ここに一項目ずつ足し、data.json の `feeds` にも「声」の学びとして残す。作り手のメモは決まりより弱いが、take の直しと合っていれば決まりにする根拠になる

## 保管庫の分け方（Claude 用と作り手用）
- **Claude 用**：`rules`（決まりごと）・`feeds`（餌箱）・`sounds`・`kufu`・`voice.json` の `vrules`。作業で読む・守るもの。アプリの「工夫」タブ
- **作り手用**：`points`（ポイント帳。アプリの「ポイント」タブ。「声」の分野は声の調整室にも出る）。作り手が読んで動画づくり・声の調整に使うコツ。`{"id","area"(声・語り・構成・見せ方・サムネ・題名・音・進め方),"tag","title","body","example","claude"(見立て),"src","srcTitle","srcOrder","order","by":"Claude"|"作り手","star","updatedAt"}`
- 作り手が記事・動画を貼って「読み込んで」と言ったら：全部読み（動画は文字起こし・画面）、①作り手が読む `points` に、やさしい言葉で一項目ずつ（見出し＋中身＋例＋Claude の見立て。裏付けがない主張はそう書く。文章の丸写しはしない）、②Claude が使えるものは `feeds` に学びとして残し、作り手の了承があるもの・はっきり効くものは `rules`（声の読み方は `vrules`）へ

## 音を付けて書き出す（声の型＋BGM）
- `python3 tools/render_draft.py --data … --proj … --repo <notion-daily> --out … --kata main --vrules --lead 0.3 --bgm <bgm.json>`（先に `bash tools/setup_engine.sh`）
- `--lead 0.3`：動画のいちばん頭に 0.3 秒の無音（ポイント帳「冒頭に 0.3秒の無音」）
- `--bgm`：`[{"from":段の番号(1から),"file":"roadmap/apps/seisakushitsu/sounds/BGM/…","vol":0.12}]`。段ごとに曲を切り替え（つなぎ目は2秒で入れ替え）、曲が短ければ重ねてくり返す。声の RMS の 0.12 倍（約 -18dB）、1.2 秒以上の間では 1.6 倍に上げる。最後に -14 LUFS にそろえ、48kHz ステレオで書き出す
- BGM は音の保管庫（data.json の `sounds[]`、kind「BGM」）から選ぶ。使った曲は `usedIn` に足し、概要欄のクレジット（`credit`）を必ず入れる
- 語りの《》は強調の印：`vrules` の `emph`（少し高く・ゆっくり）と `emph_pause`（直前に 0.45 秒の間）が効く。1本に1〜2か所まで
- take の `ref`（あれば）：作り手が自分で読んで録った声の抑揚。`f0`（10ms ごとの高さ Hz、0＝声なし）、`a`・`b`（話している範囲の秒）、`al`（10ms ごとに [0=音|1=間, 文, 句, 音, 0〜1の位置]）、`pb`（句ごとの始まり・終わりの秒。作り手が直したもの）。作り手の「理想の抑揚」なので、決まりを学ぶときは `q` より強い手がかりとして使う（例：問いかけで文末が何半音上がっているか）

## 見つけた法則は、両方の保管庫に残す（作り手の調整・直しから）
作り手の調整（声の調整室の take）や、動画・サムネ・題名への直しを反映するとき、**ほかの回にも使える法則**が見えたら、その場で次の2か所に残す。1回だけの直しは法則にしない（同じ向きの直しが2〜3回そろったら）。
1. **Claude 用**：声の読み方なら `voice.json` の `vrules`（数で）、それ以外は `data.json` の `rules`（作り手の言葉をなるべくそのまま）
2. **作り手用**：`data.json` の `points`（ポイント帳）に、やさしい言葉で一項目。`"by":"Claude"`、`"tag":"調整から"`（動画の直しなら「直しから」）、`"src"` は空、`"srcTitle"` に元にした take や直しの説明（例「問いかけの文の調整 3本から」）、`"example"` に実際の数（例「文末の2音を 半音2つ上げていた」）、`"claude"` に、決まりをどう変えたか
- 新しく法則を残したら、チャットで「ポイント帳と決まりに入れました：〜」と一行で伝える
- 前に残した法則と食い違う直しが続いたら、古いほうを直す（消さずに「（前は〜だった）」と残す）
- **全体の読み方**：調整室の「全体の読み方」のつまみは、`vrules`（scene なし）の数をそのまま書き換える（作り手が動かした決まりは `from` に「作り手が全体のつまみで」と入る。Claude は勝手に戻さない）
- **言葉での全体の注文**：`voice.json` の `notes[]` で `cat:"全体への注文"` のもの。`reply` がないものを読み、`vrules` の数（または新しい種類の決まり）に直して、`reply` に「何をどう変えたか」を書く（例「文末の下げを 1.4→2.1 半音、文と文の間を 0.15→0.25 秒にしました」）。作り手に「声の注文を見て」と言われたときと、頼みごとの片づけのついでに行う
- **読み方の辞書**：`voice.json` の `dict[]`（`surface` 書き方、`yomi` カタカナ、`accent`）。調整室で作り手が登録すると、その Mac の VOICEVOX のユーザー辞書に入る。書き出し（`render_draft.py --kata`）のときは `voice_render.sync_dict` でクラウドのエンジンにも入れるので、同じ読みになる。読み間違いを見つけたら Claude もここに足してよい（作り手に一言伝える）
- take に `recPath` があれば、作り手が録った声そのもの（`roadmap/apps/seisakushitsu/voice_rec/<id>.webm`）。録音の合わせ方（高さの測り方 YIN・時間の突き合わせ DTW）の精度を確かめ、直すときに使う

## 音の調整室（sound.html）
作り手が動画を流しながら BGM を置き・直し、メモを付けて残す所（声の調整室と同じく、直しから Claude が BGM の付け方を覚える）。
- `projects[].sound.base`＝`{"video":"…/videos/<id>/base_vN.mp4","json":"…/base_vN.json"}`：BGM なし（声と効果音だけ）の軽い動画（960x540）と、段の時刻・声の有無（`talk`、0.05秒ごと）・声の大きさ（`vr`）。`render_draft.py … --base-out <base.mp4>` で本番と同時に作れる
- `projects[].sound.bgm`＝`{"duck":間で上げる倍率(1.6),"cues":[{"id","at":秒,"soundId"（音の保管庫の id）,"vol":声に対する大きさ(標準0.12),"off":曲のどこから(秒),"fadeIn","fadeOut","none":true＝ここから音楽なし,"pts":[{"t":秒,"db":0dB＝標準}]＝大きさの変化点（曲の頭の vol から点へ直線でなめらかに変わり、最後の点のあとはそのまま）,"why":Claude のねらい},…],"by":"Claude"|"作り手","updatedAt"}`。**Claude が案を作るときは `why`（なぜこの曲・この位置か）を必ず一言入れる**。作り手が直すと `sound.claude` に Claude の元の案が残る（聞き比べ用）
- 書き出し：`render_draft.py … --bgm proj`（`sound.bgm` をそのまま使う）。調整室での聞こえ方と同じ計算（曲ごとの大きさをそろえ、声の大きさ×vol、声のない所で duck 倍、つなぎ目2秒）。`sounds[].rms` があると調整室の音量が正確になる（BGM を入れたら `rms`＝ステレオ 48kHz の二乗平均の平方根、`len`＝秒 を入れておく）
- **sound_base**（調整室用の動画を作って）：`--base-out` 付きで書き出し、`base_vN.mp4`・`.json` を `videos/<projId>/` に置いて `sound.base` を書く。まだ `sound.bgm` が無ければ Claude の案も作る（音楽の棚の role → like=1 → 印象の順、`why` 付き）。total は 2
- **sound_render**（この音で書き出して）：`--bgm proj --base-out` で書き出し、`project.video`（と `videoHistory`）を新しい版にする。`sound.base` も新しい版に。total は 2
- **学び**：`projects[].soundTakes[]`＝`{before, after, memo, learned}`。作業のはじめに `learned:false` を読み、before と after の差（曲を変えた・位置をずらした・大きさを何 dB・止めた所）とメモから、「こういう所ではこうする」を言葉にする。**同じ向きの直しが2〜3回そろったら** `rules`（scope「音」、from「音の調整室」）に足す。1回だけのものは `points`（作り手が見る）に「調整から」で残すだけ。読んだら `learned:true`、`lesson` に一言（調整室に「Claude が読んだ：〜」と出る）
- 次に BGM の案を作るときは、`rules` の scope「音」と、これまでの `soundTakes` の after を手本にする

## 音楽の棚（bgm.html）
作り手が BGM を印象で探して試聴し、保管庫（data.json の `sounds[]`、kind「BGM」）に入れる所。
- 印象（`moods[]`）の言葉：落ち着いた・穏やか・癒し・謎・ミステリー・緊張・ハラハラ・不穏・不気味・明るい・前向き・感動・壮大・弾む・軽快・ノリがいい・コミカル・しんみり・重い・暗い・神秘・幻想・勢い・推進力・アクション・激しい・荒々しい・和風（bgm.html の MOODS と同じ。足すときは両方に）
- 目録：`data/bgm_incompetech.json`（Kevin MacLeod 1443曲。feel を印象に訳したもの）。目録から入れた曲はファイルを置かず `url` で持つ（`render_draft.py --bgm` は URL なら取ってきて使う）。`catId` で目録とつながる
- 作り手の印：`like`（1＝いい・−1＝使わない・null＝まだ聞いていない）、`role`（メイン・重い回・軽い回。テイストごとに3曲を使い回すための役割）。**BGM を選ぶときは role → like=1 → 印象の順で選ぶ。like=−1 は使わない**
- **sound_collect（雰囲気の注文）**：`jobs[].wish`（言葉）と `n`（曲数）。使ってよい出どころから、注文に合う曲を `n` 曲探して `sounds[]` に入れる（`by:"Claude"`、`like:null`、`moods`、`bpm`、`len`、`source`、`license`、`credit`、`url` か `file`、`desc` に「なぜ選んだか」）。`result` に一言（入れた曲名と選んだ理由）。total は 2
- 使ってよい出どころ（規約を確かめたもの）：
  - Kevin MacLeod（incompetech.com）：CC BY 4.0。収益化可、クレジット必要（目録あり）
  - OpenTracks（旧 DOVA-SYNDROME）：商用・YouTube 可、クレジット不要。政治・宗教の内容には使えない。曲ごとの作者の条件が優先。指紋登録（Content ID）は禁止されているが、誤って申し立てが来ることはある
  - NCS（NoCopyrightSounds、ncs.io）：個人の動画なら無料・収益化可。概要欄に曲と作者のクレジット（NCS の動画の説明欄のクレジットを写す）。企業が自社の宣伝に使うのは別の許可が要る。曲調は電子音楽が多い
  - YouTube オーディオライブラリ：作り手が YouTube Studio から落として「自分で見つけた曲を足す」で入れる（ログインが要るので Claude は取れない）。「帰属表示は不要」のものが一番安全
  - YouTube にある「フリー音楽を配るチャンネル」は、曲ごとに条件がばらばら。**YouTube の動画から音を取らない**。そのチャンネルが案内する元の配布元（公式サイト）と条件を確かめてから入れる
  - Pixabay はこちらからは開けない
  - 魔王魂：CC BY 4.0。商用・報告不要、加工自由。クレジット必要（「音楽：魔王魂」、概要欄でよい）
  - 甘茶の音楽工房：商用可、クレジット任意。直リンクで鳴らすのは禁止（落として `file` で持つ）。Content ID 登録禁止。「イメージから探す」の分け方が音楽の棚の印象とほぼ同じ
  - **BGMer・MusMus は Claude が取らない**（BGMer は自動ツールでの収集・一括ダウンロードを禁止、MusMus は広告ブロック中の取得と AI に読み込ませる使い方を禁止）。作り手がブラウザで落として入れる。案内だけする
  - 注意：ニコニ・コモンズ（素材ごとに条件が違い、営利・ニコニコ外を認めないものも多い。1曲ずつ確かめる）、PeriTune（2026年8月時点で一部の曲に Content ID の申し立てが出ている）
- **出どころの一覧**：`data/bgm_sources.json`（音楽の棚の「出どころ」タブ）。`sources[]`（status：使える／使える・自分で落とす／注意／未確認／使いにくい、`fetch`：Claude／自分で、`seen`：使っていた人気動画の数と合計再生回数）と `tracks[]`（人気の動画で使われていた曲）
- **sound_scout（出どころを集め直す）**：`python3 -I tools/yt_bgm_scout.py "<探し方>" ... > out.json`。探し方はチャンネルの題材に合わせて 6〜10 個（例「ゆっくり解説 雑学」「地理 解説 なぜ」「ずんだもん 解説」）。検索は再生回数順、概要欄は innertube の next で読む（player は bot 確認で止められやすい。1本ごとに1秒あける）。結果の `sources`（既知の出どころの集計）と `new_domains`（まだ一覧にないドメイン）を見て、新しい出どころは**規約ページを読んで**から `bgm_sources.json` に足す（読めなければ status「未確認」）。曲名が書いてあるものは `tracks[]` に足す。`updated` を更新してアプリのリポジトリに入れる。`result` に「新しく見つかった出どころ・曲」を一言
- **bgm_identify（この動画の音楽を調べる）**：`jobs[]` の `url`、`at`（気になった時刻。任意、「1:30」など）、`heard`（作り手が Shazam などの聞き取りアプリで出した曲名。任意）。
  1. `python3 -I tools/yt_bgm_scout.py --video <url> [at]` で題名・チャンネル・概要欄の候補（`candidates`）・時刻付きの一覧（`timed`、`at_line`＝その時刻に当たる行）を出す。**動画から音は取らない**
  2. 曲ごとに出どころと使い方の条件を確かめる（`bgm_sources.json` にあればそれ。無ければ配布元の規約ページを読む。曲名だけなら Web で配布元を探す）
  3. `title`・`ch` と `tracks[]` を書く：`{name, by, source, url（配布元の公式ページ）, verdict, credit, note, at（流れている所。分かれば）, fetch（Claude／自分で）}`。`verdict` は「フリー素材」「フリー素材（条件に注意）」「フリー素材ではない」「分からない」のどれか。市販の曲・ゲームやアニメの曲・出どころが書いていない曲は、確かめられなければ「フリー素材ではない」か「分からない」（**推測でフリー素材と書かない**）
  4. `at` があって時刻付きの一覧も `heard` も無いときは、候補を全部並べ、`result` に「どの曲かは配布元のページで聞き比べて」と書く。概要欄にクレジットが無ければ `result` にそう書き、聞き取りアプリで曲名を出してもう一度頼むよう案内する
  5. 新しい出どころ・曲は `bgm_sources.json` にも足す。total は 1
- sound_collect に `track`（出どころタブの「棚に入れてもらう」）が付いていたら、その曲だけを配布元の公式ページから1曲取って入れる（まとめて取らない）
