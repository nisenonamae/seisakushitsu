## 0. 優先の順番

1. **最終の映像の質**。
2. 人がいつでも直せること・工程ごとに Human／Collaborative／AI を切りかえられること。
3. 速さ・自動化の割合。

設計を簡単にするときも、1 を下げる方向には簡単にしない。

## 1. 中心になる考え

**1つの「制作の文書」を、人の画面も AI も、同じ「命令」で読み書きする。**

- 絵・リグ・動き・場面・音の置き方は、すべてデータ。プログラムとして持たない。
- 文書を変える道は「命令の核」だけ。人がマウスで直しても、AI が直しても、同じ命令が同じ検査を通る。
- 度合い・許可・固定は、AI への指示文ではなく、**命令の核が強制する**。

## 2. 部品の分け方

```
┌──────────────── 画面（編集する所） ────────────────┐
│ 進行 │ 絵を描く │ リグ │ 時間の線 │ 素材の棚 │ 音 │ 点検 │
└───────────────┬────────────────────────────┘
                │命令                 ▲ 文書・断りの理由・下見
┌───────────────▼────────────────────────────┐
│ ① 命令の核：形の検査／許しの検査／前提の検査／ひとまとめに当てる／   │
│   全体の決まり／記録／取り消し／選んで取り消す    （DATA_MODEL.md 9節）│
├─────────────┬─────────────┬────────────────┤
│ ② ベクター    │ ③ 動き        │ ④ 素材と場面        │
├─────────────┴─────────────┴────────────────┤
│ ⑤ 評価：文書＋時刻 →「描く物の一覧」（純粋な計算）               │
├───────────────────────────────────────────┤
│ ⑥ 描く：一覧 → 画素。**下見も書き出しも、この同じ部品**            │
├─────────────────────┬──────────────────────┤
│ ⑦ 音と合成                  │ ⑧ 書き出しと点検                │
├─────────────────────┴──────────────────────┤
│ ⑨ 保存と同期：端末の中の控え → 送り箱 → GitHub。ぶつかりを見つける   │
└───────────────────────────────────────────┘
        ▲ 命令・提案（①を通る）       │ 文書・下見の画像
┌───────┴───────────────────────▼───────────┐
│ ⑩ 自動化：度合い・作業の札・提案・AI の作業係・見直し              │
└───────────────────────────────────────────┘
```

| 部品 | 役目 | 境目の約束 |
|---|---|---|
| ① 命令の核 | 文書を変えるただ1つの道。検査・許し・ひとまとめ・記録・取り消し | **画面・通信・時計・乱数に触らない計算**。「文書＋命令 →（新しい文書＋記録）か（断り＋理由）」。単独で試せる |
| ②③④ | 曲線・図形・合成／値の時間変化・リグ・カメラ／棚・ひな形・入れ子 | ①のデータだけを読む |
| ⑤ 評価 | 文書＋時刻 → 描く物の一覧 | 純粋な計算。同じ入力なら同じ一覧 |
| ⑥ 描く | 一覧 → 画素 | **1つだけ**。下見と書き出しで別の物を使わない（4節）|
| ⑦⑧ | 音／コマを作って動画に・機械の点検 | ⑤⑥を呼ぶだけ |
| ⑨ 保存と同期 | 記録を運ぶ。ぶつかりを見つけて知らせる | ①の記録だけを運ぶ。中身を勝手に合わせない |
| ⑩ 自動化 | だれが・どこまで | **①を通る命令しか出せない** |

## 3. 命令の核（独立した部品）

くわしい型と手順は DATA_MODEL.md 9節。ここでは、部品としての約束を書く。

- **入口は4つだけ**：`apply（当てる）`・`revert（選んで取り消す）`・`replay（記録から文書を作り直す）`・`check（当てずに、通るかだけ見る）`。
- **画面に依らない**：ブラウザでも、AI の作業場（Node）でも、同じ部品が動く。
- **試し方（画面なし）**
  - 全部の種類の命令で「当てる → 取り消す → 元と同じ」。
  - でたらめな命令の並びを大量に作って当て、「いつでも全体の決まりが保たれる」「同じ記録からは、どの端末で読んでも同じ文書」を確かめる。
  - 同じ命令を2回送っても結果が変わらない。
  - 途中で失敗する group は、何も変えない。
  - 「AI が A を変える → 人が A を直す → AI の分だけ戻す」を、効果の種類の全部の組で（DATA_MODEL.md 9.5節の表の全部の行）。
  - 許しの外の命令は、だれが送っても通らない。
- **記録から確かめ直せる**：記録には「当てた時の度合い・許可・固定」を残す。別の端末が記録を読むとき、もう一度同じ検査を通す。通らない記録（例：固定された物への AI の変更）は、どの端末でも当てない。

## 4. 下見と書き出しを同じ絵にする

### 何が食い違いうるか
同じ「描く物の一覧」を渡しても、描く部品や環境が違えば、画素は同じにならない。

| 項目 | 食い違いの元 | 手当て（案）|
|---|---|---|
| 字 | 端末に入っている字が違う・字の詰め方 | 端末の字を使わない。`library/fonts/` の字だけを読みこんで使う。読みこめていなければ描かずに不合格。題などは輪郭に変えられるようにする |
| ふちのなめらかさ | GPU で描くか CPU で描くか・拡大率 | 描く大きさを固定（1920×1080・拡大率1）。下見はその絵を縮めて見せる |
| ぼかし | 実装ごとに計算が違う【未】 | 同じ部品で描く。それでも端末で違えば、ぼかしは自前の決まった計算にする |
| 合成（重ね方・マスク）| 色の扱い（色空間・透明の掛け方）| 色空間を sRGB に固定。中間の絵の持ち方を1つに決める |
| グラデーション | 色の刻み・補い方 | 同じ部品で描く。帯が出るなら、決まったざらつきを足す |
| 画像 | 拡大縮小の補い方 | 補い方を1つに固定 |
| 線 | 細い線・端・角 | 線を核の側で輪郭の形に変えてから渡す選択肢を持つ（今の「線の部品」と同じ考え）|

### 方針
- **下見と書き出しは、同じ描く部品・同じ設定で描く。** 別々の部品を作って、あとで合わせこむことはしない。
- **「本番どおりに見る」を必ず用意する**：下見は軽くするために小さく・間引いて見せてよい。ただし、いつでも本番と同じ画素を出せる見方を持ち、点検はその絵で行う。
- **基準は書き出しの絵**。食い違ったら、下見のほうを直す。
- **両方で同じに出せない表現は、文書の形に入れない。** 入れる前に、差の試しを通す。

### 描く部品の候補
| 候補 | 同じ絵になるか | そのほか |
|---|---|---|
| R1：Canvas 2D（ブラウザの機能）を、下見でも書き出し（裏で動かす Chromium）でも | 同じ種類のブラウザなら近いはず。ただし端末の GPU・OS で描き方が変わりうる【未】。Chrome 以外では保証できない | 軽い・今と同じ・追加の読みこみなし。CPU 中心で込み入ると遅い【確】|
| R2：CanvasKit（Skia を WebAssembly で）を両方で | **同じプログラムが描くので、いちばん一致しやすい**【推】。CPU で描く設定なら端末の GPU に左右されにくい【未】 | GPU でも描ける【確】。後始末を手でする必要【確】。読みこむ物が大きい【般】。速さは要試作 |
| R3：下見は R1、書き出しは別の物 | 一致は保証できない | **採らない** |

**いまのおすすめ**：R1 と R2 を、同じ試しの場面で比べて決める（試作 P1）。決め手は速さより「一致」と「絵の質」。

### 試作 P1 に入れる「差の試し」
- 試しの場面を7つ用意する：字／ふち（細い形・斜めの線）／ぼかし／合成とマスク／グラデーション／画像の拡大縮小／線（細い・太い・端・角）。
- 同じ文書・同じ時刻のコマを、①作り手の端末の下見（Mac・Chromebook）②書き出しの環境（作業場・Mac）で描き、画素を比べる。
- 見る数字：違う画素の割合・いちばん大きい色の差。合格の線は、まず「見比べて分からない」を人の目で決め、その時の数字を基準にする（要調整）。
- この試しは、のちに毎回の自動の試しとして残す（描く部品を直したら必ず流す）。

## 5. 保存と同期・認証

### 今の実装【確：コードを読んだ】
- 認証：作り手が設定の欄に **fine-grained の個人用トークン**（データのリポジトリの Contents を読み書きできる物）を打ちこむ。端末の `localStorage`（`gh_t`）に入り、`Authorization: Bearer` で GitHub API に送る。「ほかの端末に設定を渡す」で、設定を文字列として写せる。
- **公開している JavaScript にも、リポジトリのどのファイルにも、トークンは入っていない**（探して確かめた）。
- 保存：GitHub の contents API に、前に読んだ `sha` を付けて書く。食い違うと 409／422 が返り、読み直して合わせてから書き直す。
- 分かっている弱み：
  - GitHub Pages では、同じ持ち主のアプリが**同じ場所（オリジン）**で動く。`localStorage` は場所ごとなので、**同じ持ち主のどのアプリのページからもトークンが読める**【般】。どれか1つに悪いスクリプトが入れば漏れる。今は外部のスクリプトを1つも読みこんでいない【確】ので、入口は小さい。
  - トークンが届く範囲は、データのリポジトリ全体（ほかのアプリのデータも同じリポジトリにある）。

### これからの決まり
- **秘密のトークンを、公開する JavaScript・文書・記録・提案に入れない。**（今も守れている。続ける）
- トークンは作り手の端末の中だけ。AI の作業係は、作り手のトークンを使わない（作業場が持つ自分の権利で読み書きする）。
- 外部のスクリプトを読みこまない方針を続ける。読みこむ場合は、中身を固定して自分の所に置く。
- ビルドを使うようになっても、ビルドにトークンを渡さない。

### 認証の選択肢（決めていない。人の判断が要る）
| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| A1：今のまま | 個人用トークンを端末に置く | 新しいトークンが要らない（作り手の約束）| 上の弱みがそのまま |
| A2：今のまま＋守りを足す | 外部スクリプトなしを決まりにする・ページに読みこみ元の制限を付ける・トークンに期限を付けて時々替える | 手間が小さい | 同じ場所のほかのアプリからは読める |
| A3：データの置き場を分ける | 制作室だけの private リポジトリと、それだけに届くトークン | 漏れても届く範囲が小さい | **新しいトークンが要る**（約束とぶつかる）。データの引っこし |
| A4：場所を分ける | 制作室だけ別のドメインで動かす | ほかのアプリから読めなくなる | ドメインの用意。トークンの打ち直し |
| A5：トークンを置かない方式 | GitHub の認証の流れを使う | 端末に長く残る秘密が減る | 中継ぎのサーバーが要る可能性が高い【未】＝新しい契約 |

**いまのおすすめ**：A2 で始め、A3 か A4 を作り手が選べるように残す。

### 同期の設計（まず、安全に見つける）
- **正本は記録**（足すだけ）。端末ごとに別のファイルに書くので、2台が同じファイルを取り合わない。
- **書く前に、端末の中に控える**：命令は、①端末の中の送り箱に書く → ②画面に反映 → ③GitHub に送る → ④届いたと確かめてから送り箱から消す、の順。途中でアプリが落ちても、通信が切れても、送り箱から送り直せる。同じ命令が2回届いても、id で見分けて1回しか当てない。
- **読むとき**：ほかの端末の新しい記録を取ってきて、命令の核に順に通す。重ならない変更は自動で入る。同じ所への変更は「ぶつかり」として残し、画面で選ぶ（DATA_MODEL.md 9.6節）。
- **古い状態から書こうとしたら**：前提の版が合わないので、重なる所があれば核が断る。画面は読み直す。アプリ自体が古い版のとき（今の `pageStale` の守り）は、送らずに読みこみ直しを促す。
- 最初から CRDT などは入れない。ぶつかりが多くて困ると分かってから考える。

### GitHub を置き場にすることの限界【未】
- 書くたびにコミットが増える。まとめて送る間隔を決める必要がある。
- 1時間あたりの回数に上限がある【般】。1回の往復に時間がかかる。
- 何個かのファイルを一度に、全部か無しかで書く方法が使えるかは、P3 で確かめる。

## 5b. 順番・送り主・トークン（追加の検討。**案・作り手の承認待ち**）

改訂2のあとで見つけた問題と、その手当ての案。承認されたら、DATA_MODEL.md 9.6節・AUTOMATION_DESIGN.md 3節を書き直す。

### 見つけた問題
- **端末をまたぐ順番が決まっていなかった**：「端末ごとの番号と端末の組で並べる」だけでは、オフラインだった端末の古い命令が、あとから過去の位置に割りこみ、すでに見えていた結果が書きかわる。
- **送り主を名乗りで信じていた**：命令の `actor` は送る側が自由に書ける。コミットの書き手も、API で作るときに自由に指定でき、署名も無い【確：今の履歴と API の説明】。
- **共有する物があいまいだった**：共有するのは命令だけ。効果・版の変化（Applied）は、各端末が同じ計算で作り直す。

### 順番：小さな「順番の台帳」
- 各端末は、命令のまとまりを、自分専用の**書きかえないファイル**に書く。
- 次に、**順番の台帳**（1つの小さなファイル）の末尾に、そのまとまりの番号を足す。足すときは「前に読んだ版と違えば断られる」方式（今の保存と同じ）。断られたら読み直して足し直す。
- **全端末の順番＝台帳に並んだ順**。時計も、端末内の番号どうしの比べも使わない。
- 命令は「書いたとき、台帳のどこまでを見ていたか」の数を1つ持つ。それより後ろに入った他人の命令が「同時だった命令」。値の道ごとに比べる（DATA_MODEL.md 9.6節の決まり）。これ以上の因果の記録（ベクター時計など）は入れない。
- オフラインだった端末の命令は、台帳の**末尾**に入る。過去は書きかわらない。同じ端末の番号が飛んでいたら、埋まるまで待つ。専用ファイルは書けたが台帳に足す前に落ちた分は、起動時に足し直す。
- 弱み：書くたびに往復が1回増える／台帳が1か所に集まる／長くなったら区切る処理が要る。

### 送り主：4つを分け、権限は確かめられた物からだけ決める
| 分ける物 | 何で決めるか |
|---|---|
| 実行した主体 | 命令に書く（参考。権限には使わない）|
| 承認した主体 | **端末の鍵による署名**。承認した提案の中身のハッシュに掛ける |
| 送信した端末 | どの専用ファイルに入っているか＋その端末の署名 |
| 実際の権限 | 核が計算する：正しい署名があれば人、無ければ（何と名乗っても）AI |

- 鍵は、ブラウザの機能で端末の中に作り、取り出せない形で持つ。信頼する端末の一覧は各端末が自分の中に覚え、新しい端末は、信頼済みの端末が署名して認める。
- **今の構成（GitHub Pages＋GitHub API）でできる**：人の端末が自分の承認を証明する・偽の承認を当てない・承認と提案の中身を結ぶ。
- **サーバー側の仕組みが要る**：AI が偽の記録を書くこと自体を止める・失くした端末を全体で確実に無効にする・信頼できる時刻と改ざんできない監査の記録・AI の作業場での再生を偽の承認から守る。
- だから、**公開の最終確認は、作り手の端末で行う**。
- 残る穴：AI が作り手のブラウザを直接操作できる状態では、端末の鍵で承認できてしまう。使い方の決まりで守るしかない。

### トークン
| 案 | 安全性 | 作る手間 | 続ける負担 |
|---|---|---|---|
| 今のまま | 同じ場所のどのページからも読める。届くのはデータのリポジトリ全体 | なし | なし |
| 権限を最小にする | 漏れたときの被害が小さくなる。読まれること自体は防げない | 小 | 小【未：今あるトークンを作り直さずに狭められるか】|
| 別の場所（オリジン）に分ける | ほかのアプリから読めなくなる | 中 | 小（1回打ち直す）|
| 仲介するサーバー | 端末に長く残る秘密が無くなる。送り主の問題も一緒に解ける | 大 | 大（契約・保守）|

- **試作の間（暫定）**：今のまま。P4・P3a・P1・P2 はトークンに触らない。試作に外部のスクリプトを読みこまない。P3b の本物での確認は、今あるトークンで、データの置き場の中の試し用フォルダに書く。
- **将来**：本番で人の承認を扱う前に、別の場所に分ける。仲介のサーバーは、複数人で使う・AI を無人で長く動かす、となったら検討。

### 試作の置き場（確かめた）
- 今のリポジトリの中の独立したフォルダでよい。今あるファイルに触らなければ、制作室の動きは変わらない。インストール用の仕組み（`sw.js`）は何も貯めない作りで、試作のページに干渉しない【確】。
- push のたびに公開の組み立てが走る。1時間に10回がゆるい上限【確】なので、試作の push はまとめる。組み立てが失敗しても、今の制作室は前の版のまま動く【般】。
- 同じ場所なので、試作のページからもトークンが読める。上の決まりで守る。

## 6. 技術の選び方（比べる）

### 6.1 自前で完結させる（作り手の決定・2026-11-27）

- **制作の工程は、最終的に自前の道具で完結させる。** 描画・ベクター編集・リグ・アニメーション・場面の編集・カメラ・声・効果音・音楽・書き出しまでを1つにまとめる。
- **既存の有料の制作ソフト（After Effects・Illustrator など）を、工程の中核に置かない。** 使える環境も無い。それらは「学ぶ相手」（PRODUCT_REQUIREMENTS.md 2節）であって、「使う道具」ではない。
- **外部ライブラリや描くエンジンは使ってよい。** 外部ライブラリを使うことと、既存の制作ソフトに依存することは別。
- **自前であること自体を目的にしない。** 目的は最終の映像の質。自前で書くと質が下がる所は、外部ライブラリを選ぶ。

**外部ライブラリを使うときの条件**
| 条件 | 理由 |
|---|---|
| 自分の所に置いて使える（外部の配信元から読みこまない）| トークンと同じ場所に外部のスクリプトを入れない。止まっても動く |
| 使用の条件が、公開する動画・公開するコードで問題ない | あとで差しかえになるのを防ぐ |
| 月々の契約・新しい鍵が要らない | 作り手の約束 |
| 取りかえられる（境目の内側に閉じこめる）| 文書の形（データ）は自分で持つ。ライブラリの独自形式を正本にしない |
| 下見と書き出しで同じ結果になる | 4節 |

**いま分かっている、外部の物を使う所**（どれも制作ソフトではない）：描くエンジンの候補（CanvasKit）／動画に包む部品（ffmpeg）／声（VOICEVOX）／裏で動かすブラウザ（書き出し）。どれを続けるかは試作で決める。

**参考にする既存の道具**（乗らない。考え方を学ぶ）：Rive（人と AI が同じデータを触る）・Cavalry（決まりで作る 2D）・Motion Canvas（コードで動画。今の制作室と同じ系統で、その弱みが今回の動機）。

### 6.2 自前で作る場合
| 決めること | 選択肢 | いまのおすすめ |
|---|---|---|
| 言語とつくり | 素の JS・1ファイル／TypeScript＋部品に分けてビルド／デスクトップのアプリ | TypeScript＋部品。命令の型から検査を作れる。同じ核をブラウザでも作業場でも動かせる |
| 描く部品 | 4節の R1／R2 | **P1 で決める** |
| 書き出し | 同じ描く部品で1コマずつ → 損のない形で ffmpeg へ／ブラウザの中で直接エンコード | 本番は前者。後者は下見の書き出しに試す。タブを切りかえるとエンコーダーが止まることがある【確】|
| 動きの持ち方 | 鍵だけ／鍵＋式／ノード | 鍵＋式（小さな専用の言葉。DATA_MODEL.md 3節）|
| 保存と同期 | 5節 | **P3 で確かめる** |
| 認証 | 5節 | **人が決める** |
| AI の動かし方 | 会話で頼む／予約タスク／アプリから API | 前の2つ（新しい鍵が要らない）|

## 7. 今の制作室との関係
- 建て増しではなく、別に建てて、できた所から移す。今の制作室は動かしたまま。
- 進行・候補・ポイント・運営・声・音は、当面いまのページ。新しい仕組みはまず「絵・リグ・動き・場面」。
- つなぎ目：今の `shots` に `{"t":"doc","scene":id}` を足す【推】。

## 8. 危険と手当て
| 危険 | 大きさ | 手当て |
|---|---|---|
| 道具づくりが終わらず、動画が出ない | 特大 | 段階ごとに本物の場面を1つ。範囲の外は作らない |
| 既存のソフトと比べないので、質の天井が分からない | 大 | 節目ごとに手本と並べる（P4・M2・M6）|
| 1人では量が足りない | 大 | 濃さを保って長さ・場面数を選ぶ。資産をためる |
| 絵の質が道具では上がらない | 大 | 手本の分析・決まり・見直しを並行。**P4 を早く** |
| 下見と書き出しが食い違う | 大 | 同じ描く部品。差の試しを毎回 |
| 選んで取り消すが、聞く場面だらけで使えない | 中 | P3 で実際の操作の並びで測る。多ければ命令の細かさを見直す |
| 同期でデータが消える（過去に起きた）| 中 | 記録は足すだけ・端末ごとに別ファイル・送り箱・ぶつかりは残す |
| トークンが漏れる | 中 | 5節。外部スクリプトなし。届く範囲を小さくする案を人が選ぶ |
| AI が良い物を壊す | 中 | 固定・許可・提案を、核が強制 |
| 設計が大きすぎる | 中 | 最初に作るのは①⑤⑥と、②の一部だけ |

## 9. 改訂2の影響（大きい変更）
- **命令と記録の形が変わった**（DATA_MODEL.md 9節）。理由：前の形（`op:string`・`args:any`・`undo:any`）では、検査も、AI の変更だけを戻すことも保証できない。影響：点・鍵に id が要る／部品に版の番号が要る／動かす操作を「足す量」で持つ。まだ何も作っていないので、作り直しは起きない。
- **描く部品を1つにした**。理由：下見と違う絵が書き出されると、質の判断がすべて信用できなくなる。影響：⑥を取りかえる自由は残るが、「下見用と本番用に2つ持つ」はしない。
- **記録を端末ごとのファイルにした**。理由：同じファイルの取り合いをなくす。影響：読むときに何個かのファイルを集める。
