# 仕組みの設計（SYSTEM_ARCHITECTURE）

2026-11-27。この文書は**案**。技術はまだ決めていない。3節で選択肢を比べ、「いまのおすすめ」と「試作で確かめること」を分けて書く。

## 1. 中心になる考え

**1つの「制作の文書」を、人の画面も AI も、同じ「命令」で読み書きする。**

- 絵・リグ・動き・場面・音の置き方は、すべてデータ（文書）として持つ。プログラムとして持たない。
- 文書を変える方法は「命令」だけ（例：点を動かす・キーフレームを打つ・部品を足す）。人がマウスで直しても、AI が直しても、同じ命令が記録される。
- だから：取り消しが全部に効く／AI のしたことが1つずつ見える・戻せる／工程ごとに人と AI を入れ替えても、データも画面も同じ。

これが「3つのやり方を、別のアプリや別の流れにせず、同じ制作で使える」ための条件になる。

## 2. 部品の分け方

```
┌──────────────── 画面（編集する所） ────────────────┐
│ 進行  │ 絵を描く │ リグ │ 時間の線 │ 素材の棚 │ 音 │ 点検 │
└───────────────────┬────────────────────────┘
                    │ 命令（人）            ▲ 状態・下見
┌───────────────────▼────────────────────────┐
│ ① 文書の核：形の決まり・命令・取り消し・検査・版の移し替え        │
├──────────────┬──────────────┬───────────────┤
│ ② ベクター     │ ③ 動き         │ ④ 素材と場面       │
│ 形・曲線・合成 │ キーフレーム・式 │ 棚・ひな形・入れ子   │
│               │ リグ・カメラ    │                    │
├──────────────┴──────────────┴───────────────┤
│ ⑤ 評価：文書＋時刻 →「描く物の一覧」（同じ入力なら必ず同じ結果）     │
├─────────────────────┬──────────────────────┤
│ ⑥ 描く：一覧 → 画面／画像     │ ⑦ 音と合成：語り・効果音・BGM   │
├─────────────────────┴──────────────────────┤
│ ⑧ 書き出しと点検：コマを作る → 動画。機械の点検                  │
├───────────────────────────────────────────┤
│ ⑨ 保存と同期：小分けのファイル・履歴・GitHub                    │
└───────────────────────────────────────────┘
        ▲ 命令（AI）・提案           │ 文書・下見の画像
┌───────┴───────────────────────▼───────────┐
│ ⑩ 自動化：工程ごとの度合い・許可・提案と承認・AI の作業係・見直し   │
└───────────────────────────────────────────┘
```

| 部品 | 役目 | ほかとの約束（境目） |
|---|---|---|
| ① 文書の核 | データの形、命令の適用・取り消し、検査 | 画面にも AI にも依存しない。単独で試せる |
| ② ベクター | 曲線の計算・図形・合成・清書・当たり判定 | 入力も出力も①のデータ |
| ③ 動き | 値の時間変化（キーフレーム・式・リグ・カメラ）を解く | 「文書＋時刻 → 値」だけ |
| ④ 素材と場面 | 棚・ひな形と写し・入れ子・版 | 参照は id で |
| ⑤ 評価 | 文書＋時刻 → 描く物の一覧（形・色・変形・重なり） | **純粋な計算**。画面にも乱数にも時計にも触らない |
| ⑥ 描く | 一覧を Canvas などに描く | ⑤の一覧だけを受け取る。取りかえられる |
| ⑦ 音と合成 | 時間の線に音を置き、混ぜる | 時刻の合図は③と共有 |
| ⑧ 書き出しと点検 | コマ → 動画。機械の点検 | ⑤⑥⑦を呼ぶだけ |
| ⑨ 保存と同期 | ファイルの読み書き・ぶつかりの解決 | ①の命令の記録を運ぶ |
| ⑩ 自動化 | 度合い・許可・提案・AI の作業係 | **①の命令しか使えない** |

大事な境目は2つ。
- **⑤（評価）を純粋な計算にする**：下見も本番も、作り手の画面も AI の環境も、同じ絵になる。点検も AI の見直しも、この1つを呼べば済む。
- **⑩（自動化）は命令しか使えない**：AI に裏口を作らない。人の画面でできないことは AI にもできない。

## 3. 技術の選び方（比べる）

### 3.1 そもそも、自前で作るのか

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| A. 既存の道具を AI が動かす | Illustrator＋After Effects を、スクリプトで Claude が操作 | 質の天井は証明済み（kurzgesagt と同じ道具）。機能を作らなくてよい | 月々の費用。Mac の中でしか動かず、今の「チャットから push」の流れに乗らない。AI が画面を見て確かめにくい。データの形が道具まかせで、人と AI の切りかえ・提案と承認・取り消しを自分で設計できない。**作り手が AE を覚える必要がある**【推】 |
| B. 人と AI 向けの既存の道具に乗る | Rive・Cavalry など | 骨・式・手続きがすでにある。Rive は AI から CLI で作れる | 用途がアプリ向け（Rive）か、AI から触る道が弱い（Cavalry）。語りとの同期・工程・品質の点検は結局自前。独自形式に縛られる |
| C. コードで動画を書く枠組みに乗る | Motion Canvas・Remotion | 今の作り方に近く、移しやすい | 「絵と動きがプログラム」という今の一番の弱みがそのまま残る |
| D. 自前で作る | この文書の設計 | 人と AI の協働・語りとの同期・段・決まりを中心に置ける。今の流れ（GitHub・スマホ・チャット）に乗る | **作る量が非常に多い**。Illustrator＋AE 級は1人では不可能。範囲を絞らないと完成しない |

**いまのおすすめ：D。ただし範囲を「ベクターの解説アニメ」に絞る。A は捨てずに「比べる相手」として1度試す。**
- 理由：この制作の中心の価値は「工程ごとに人と AI を切りかえる」ことで、それは道具の中身（データと命令）を自分で持たないと作れない。
- 正直な危険：D は道具づくりが目的になって動画が出なくなる危険が一番大きい。だから IMPLEMENTATION_ROADMAP.md では、各段階で必ず「本物の場面を1つ作る」を合格条件にする。
- A を試す意味：もし「Claude が AE のスクリプトを書く」だけで十分な質と流れが得られるなら、D の大半は要らない。1日で確かめられるので、作り始める前に確かめる（試作 P0）。

| 保存と同期 | ①今のまま（1つの JSON を丸ごと）②小分けのファイル＋命令の記録を GitHub に③端末の中に持ち、git で同期④専用のサーバー | ②は今のトークンで動き、ぶつかりを「命令の順番」で解ける。③はパソコンでは最良だがスマホが弱い。④は新しい契約と鍵が要る（作り手の約束に反する）。**おすすめ②**。ぶつかりの解き方は試作で確かめる |
| AI の動かし方 | ①今のまま（人が会話を開く）②予約タスクで定期的に③アプリから API を直接呼ぶ | ③は新しい鍵と費用が要る。**おすすめ：①②を「作業係」として整える**（AUTOMATION_DESIGN.md）。仕組みは③に差しかえられる形にしておく |

## 4. 今の制作室との関係

- **建て増しではなく、別に建てて、できた所から移す。** 今の制作室は動かしたまま（動画づくりを止めない）。
- 進行・候補・ポイント・運営・声・音は、当面いまのページを使う。新しい仕組みはまず「絵・リグ・動き・場面」を受け持つ。
- つなぎ目：今の `shots`（`{"t":"html",…}`）に、新しい種類 `{"t":"doc","scene":"<場面の id>"}` を足せば、今の書き出しの流れから新しい場面を呼べる【推】。
- 今ある場面（JS で描いた物）は、無理に移さない。新しい動画から新しい仕組みで作る。

## 5. 危険と、その手当て

| 危険 | 大きさ | 手当て |
|---|---|---|
| 道具づくりが終わらず、動画が出ない | 特大 | 段階ごとに「本物の場面を1つ」。範囲の外は作らない。P0 で A 案と比べる |
| 1人では量が足りない（kurzgesagt は1本1,200時間） | 大 | 濃さを保って長さ・場面数を選ぶ。素材と動きを資産としてためる。AI の受け持ちを増やす |
| 絵の質が道具では上がらない（作り手・AI の腕の問題） | 大 | 道具と並行して、手本の分析・決まり・見直しを続ける。道具は「直せる」ことを保証するだけ |
| ブラウザの描く力が足りない | 中 | ⑤⑥を分けて取りかえられるように。P1 で早く確かめる |
| 同期でデータが消える（過去に実際に起きた） | 中 | 命令の記録を足すだけの方式。丸ごとの上書きをしない。毎日の写し |
| AI が勝手に変えて、良かった物が壊れる | 中 | 固定・提案と承認・変更ごとの取り消し（AUTOMATION_DESIGN.md）|
| 設計が大きすぎて複雑になる | 中 | 部品は10個だが、最初に作るのは①②⑤⑥だけ。あとは要るときに |
