# 今の制作室の調べ（CURRENT_STATE_AUDIT）

調べた日：2026-11-27。調べた物：`nisenonamae/seisakushitsu`（アプリ）と `nisenonamae/notion-daily` の `roadmap/apps/seisakushitsu/`（データ。読んだだけ）。
印の意味：**【確】**＝コード・データを実際に見て確かめた／**【記】**＝CLAUDE.md などの記録にある（今回は測り直していない）／**【推】**＝そこからの推測。

## 1. ひとことで

今の制作室は「動画を1本作る段取りと、Claude への頼みごとを回す道具」としてはよくできている。けれども **絵とアニメーションは「データ」ではなく「プログラム」として存在している**。これが、質を上げるうえでの一番の壁になっている。

## 2. 全体のつくり【確】

| 層 | 中身 | 技術 |
|---|---|---|
| 画面（アプリ） | `index.html`（274KB）`draw.html`（331KB）`voice.html`（90KB）`parts.html`（86KB）`sound.html`（75KB）`bgm.html`（37KB） | 1ページ＝1ファイルの素の HTML/JS。外部ライブラリなし・ビルドなし。GitHub Pages で公開。PWA（`sw.js`） |
| データ | `data.json`（2.26MB）`voice.json`（166KB）＋ 素材のファイル（合計 1.4GB。うち動画 1.2GB） | private リポジトリに JSON と画像・動画・音を置く。画面から GitHub API で直接読み書き |
| 作る道具 | `tools/`：Python（直下と `vis/` で約3,250行。`kahitsu/` は別）＋ JS 数本 ＋ 場面のページ | Python（PIL・numpy）＋ ffmpeg ＋ Playwright（Chromium）＋ VOICEVOX |
| AI | アプリの中に AI の呼び出しは**ない** | 画面が `jobs`（頼みごと）を data.json に書く → 人が Claude の会話を開く → Claude が `tools/WORKER.md`（576行・20節）の手順で片づけて結果を書き戻す |

- ページどうしは同じ data.json を共有する。それぞれが自分の `merge` を持つ（6ページに同じ意味のコードが散らばる）。
- 自動テスト：`draw_selfcheck.js`（93行）`sync_stale_check.js`（27行）`lint_shots.py`（87行）`scene_measure.py`（78行）だけ。テストの枠組みはない。

## 3. データの形【確】

`data.json` のおもな項目（大きい順）：`projects`（7本・1.1MB）`materials`（14）`feeds`（22）`rules`（117）`arts`（6）`jobs`（77。できた72・待ち4・失敗1）`points`（55）`sounds`（23）`candidates`（30）`ops`（20）。

- 1本の制作（project）がとても大きい：いちばん大きい物で `flesh`（肉付け）299KB・`outline`（構成）189KB・`videoHistory` 56KB。**文章・場面の指定・履歴が1つのかたまり**に入っている。
- **場面の指定はこの形**：`{"t":"html","page":"lawater","mode":"mismatch","ats":["青で","北の方",…]}`。つまり「どのページの、どのモードを、語りのどの言葉で進めるか」だけ。**絵の中身・動きはここには無い**（ページの JS の中）。
- お絵描きの絵（`arts`）：レイヤーごとの PNG（`art/` に 113枚）。**ラスター（点の絵）**で、ベクターではない。
- 部品（`parts/`・`tools/kahitsu/packs/`）：`{pts:[[x,y]…], color, z, parent, joint, line, folder, hide}`。閉じた形・1色・線なし・グラデーションなし。
- **ごみが混ざっている**：data.json のいちばん上に `sha`・`git_url`・`download_url`・`_links`・`content`（空）など、GitHub API の返事の項目がそのまま入っている。どこかの書き込みが返事ごと保存した跡【推】。害は見えないが、データの形が守られていない証拠。

## 4. 絵とアニメの実装【確】

2つの系統がある。

1. **Python で描く古い部品**（`tools/vis/scenes.py` ほか）：PIL で1コマずつ描き、ffmpeg に流す。`photo`・`map`・`cards` など20種類以上。洗濯板道路のころの物。
2. **ブラウザで描く場面**（`tools/vis/html/` に 58ファイル・1.33MB）：動画ごとに HTML/JS のページを書く（例 `arabia.html` 46KB＋`arabia_intro.js` 75KB）。中身は `render(t)` という関数で、**時刻 t を受け取って Canvas に全部描き直す**。カバも木も「`hp3(x,y,…)` のような描く関数」。

書き出し（`tools/vis/parts3.py`・`render_draft.py`）：
- Playwright でページを開き、1コマごとに `render(n/30)` を呼んで **`canvas.toDataURL('image/jpeg',0.96)`** で取り出す → MJPEG として ffmpeg へ → libx264。
- 大きさは 1280×720 が基準（本番は倍率を掛けて 1080・1440）。**30fps 固定**（`W,H,FPS=1280,720,30`）。
- 場面と声は、指定＋コード＋素材のハッシュでキャッシュする。【記】序＋第1章（1分41秒）の書き出しが 154秒 → 直したあとは 25秒。
- 音：Python（numpy）で声・効果音・BGM を混ぜ、−14 LUFS にそろえる。声は VOICEVOX。

## 5. 強み（残す価値があるもの）

| もの | なぜ残すか |
|---|---|
| **語りの言葉で場面を進める（`ats`）** | 絵のタイミングを秒でなく「語りのこの言葉」に結ぶ。語りを直しても絵がずれない。解説動画にとても合っている |
| **段を分けて作る（0設計〜6仕上げ）** | 作り手が決めた品質の進め方。新しい仕組みの「工程」の土台になる |
| **決まりの3段（部品・機械・読む）と `rules_for.py`** | 決まりが増えても重くならない仕組み。品質基準の土台 |
| **見直しループ・見直しのサイクル（別の Claude が見る・2案比べ・負けたら戻す）** | 自動化の品質の守りとして、そのまま「AI主導」の中身になる |
| **実物帳・手本帳・指摘帳** | 絵の質を上げた実績がある（「実物を学ぶとよくなる」） |
| **頼みごと（jobs）と章ごとの確認** | 人と AI の受け渡しの原型。新しい「提案と承認」に育てられる |
| **声の調整・音の調整室** | 音まわりは比較的できあがっている。当面そのまま使える |
| **ハッシュでのキャッシュ・1命令の書き出し** | 直したあとの速さに効いている |
| **部品で直す（parts.html）で分かったこと** | 少ない点・図形から・線の部品・フォルダ・付け根。新しいベクターの土台の要件 |
| **同期の事故から学んだ守り** | 古い画面の上書き防止・sha を指定して読む・自動の書き換えで時刻を進めない |

## 6. 弱み（技術の借金）

**A. 絵と動きがプログラムである（いちばん重い）**【確】
- 絵を直すには JS を書き直すしかない。作り手が手で直せない。だから `cap_art.py` で「Canvas への描く命令を横取りして部品に戻す」という回り道が要った。
- 動き・カメラ・タイミングも式の中。**キーフレームも、時間の線（タイムライン）も、グラフも無い**。「この動きを少し遅く」が人の手でできない。
- 動画ごとに新しいページを書くので、素材も動きも使い回しにくい。作った物が資産としてたまらない。

**B. ベクターの表現が足りない**【確】
- 取っ手のない曲線（点を通る自動の曲線だけ）。線（輪郭線）・グラデーション・ぼかし・マスク・形の合成（足す・くり抜く）が無い。
- 手描き（draw.html）はラスターで、動きの部品にするには別の変換が要る。

**C. 書き出しの画質に損がある**【確】
- 1コマごとに JPEG（品質 0.96）にしてから、もう一度 H.264 に圧縮している。平らな色と細い線が命の絵柄では、にじみ・色の帯が出うる【推。見比べは未実施】。
- 30fps 固定。kurzgesagt は 60fps で教えている（出典は PRODUCT_REQUIREMENTS.md）。

**D. データが1つの大きなファイル**【確】
- data.json 2.26MB を、6ページが丸ごと読んで丸ごと書く。1MB を超えて API の読み方を変える必要が出た・古い画面が上書きした・時計のずれで負けた、という事故が実際に起きている【記】。
- 形の決まり（スキーマ）と検査が無い。3節のごみがその結果。

**E. コードが大きな1ファイルに固まっている**【確】
- `draw.html` は 331KB が1ファイル（`function` のある行が303）。同じ処理（同期・merge）が6ページに重複。部品として取り出して試すことができない。

**F. 自動化が「会話を開く人」に頼っている**【確】
- AI の仕事は、人が Claude の会話を開いて頼むと動く。工程ごとに「人がやる／一緒にやる／AI に任せる」を切りかえる仕組みは無い。
- AI がしたことの記録は data.json の結果と git の履歴だけ。「この変更だけ取り消す」はできない。

**G. 取り消しと履歴が弱い**【確】
- parts.html の取り消しは、素材まるごとの写しを60回分。draw.html は別の仕組み。動画の場面には取り消しが無い。

## 7. 足りない機能（kurzgesagt 級に要るのに、今ないもの）

ペンツール（取っ手つきの曲線）／線と塗りの分離・グラデーション／形の合成／色の一括管理／部品のひな形と差し替え（インスタンス）／骨・関節・逆運動（IK）／キーフレームと速度のグラフ／式（くり返し・揺れ・遅れてついてくる）／カメラと奥行き（2.5D）／場面の入れ子／マスク・合成モード・ぼかし／大量に並べる仕組み（草・群れ）／60fps・損のない書き出し／工程ごとの自動化の切りかえ／変更ごとの取り消し。

## 8. 結論

- **残すのは「考え方」と「音まわり」**。段取り（工程・決まり・見直し・語りの言葉で進める）は新しい仕組みの骨格になる。
- **作り直すのは「絵と動きの持ち方」**。プログラムではなく、人も AI も同じように読み書きできる**データ（場面の文書）**にする。今の建物の上に足すのではなく、土台から別に建てて、できた所から移すのがよい。
- 今のコードで技術的にそのまま使えそうなのは：曲線の式（`HND`）・清書（`fitPts`）・語りと時刻の対応づけ・音の混ぜ方・キャッシュの考え・点検の道具。ただし取り出して部品に直す必要がある【推】。
